## 전체 검색 파이프라인

```
1. 질의분석 결과 수신
   ├─ 단일·동일업무 복합질의: 검색 질의 1개
   └─ 교차업무 복합질의: 원문 + 분해질의 여러 개
   ↓
2. 각 검색 질의별 질문 임베딩
   └─ HCX bge-m3
   ↓
3. 각 검색 질의별 1차 후보 검색
   ├─ Dense Structured V2 Top-20
   └─ BM25 Nori-none Top-20
   ↓
4. Dense·BM25 점수 Min-Max 정규화
   ↓
5. 7:3 가중 합산
   └─ Hybrid 후보 Top-20
   ↓
6. 검색 질의가 여러 개면 가중 RRF(K=10) 결합
   └─ 통합 후보 Top-20
   ↓
7. BAAI CrossEncoder Reranker
   └─ 후보 20개를 원질의 기준으로 재정렬
   ↓
8. 최종 Child Top-5 선택
   ↓
9. Parent-Child8192 문맥 확장
   ├─ 검색된 Child는 그대로 유지
   ├─ 같은 Parent의 인접 Child 추가
   └─ Parent당 최대 8,192자
   ↓
10. 답변 B 시스템의 Basic Evidence Pack으로 전달
```

---

## 1. 질의분석 결과 수신

검색 시스템은 사용자 원문을 직접 받는 것이 아니라, 질의분석 시스템이 만든 검색계획을 받습니다.

### 단일질의

```
질문:
채무조정 신청하려면 어떻게 해야 하나요?

검색계획:
ORIGINAL · 1.0
```

검색 질의 하나만 실행합니다.

### 멀티턴 후속질의

```
사용자 질문:
신청 서류는 어떻게 돼?

검색용 독립질의:
채무조정 관련 신청 서류는 어떻게 돼?

검색계획:
ORIGINAL · 1.0
```

사용자 원문이 아니라 문맥 업무가 안전하게 결합된 독립질의를 검색합니다.

### 승인된 교차업무 복합질의

```
사용자 질문:
미수령금 조회 방법과 착오송금 반환 신청 방법을 알려주세요.

검색계획:
원문                                0.4
미수령금 조회 방법                  0.3
착오송금 반환지원 신청 방법         0.3
```

각 검색 질의를 독립적으로 Hybrid 검색한 후 결과를 다시 결합합니다.

---

## 2. 검색 문서 구성

현재 Dense와 BM25 모두 같은 기본 문서 내용을 사용합니다.

```
문서 제목
소제목
본문
```

코드상 구성은 다음과 같습니다.

```
title
section_title
content
```

예를 들어 하나의 검색 문서는 개념적으로 다음과 같습니다.

```
착오송금 반환지원 FAQ
반환지원 신청 대상
착오송금인이 금융회사를 통해 반환을 요청했으나...
```

이를 `Dense Structured V2`라고 부릅니다.

중요한 점은 문서를 다음처럼 구조화한다는 뜻이지, 별도 JSON이나 복잡한 메타데이터를 임베딩한다는 뜻은 아닙니다.

```
제목 + 소제목 + 본문
```

URL, chunk ID, 업무 필터 등의 메타데이터는 임베딩 텍스트에 포함되지 않습니다.

## 3. Dense Structured V2 검색

### Dense 검색이란?

문장에 같은 단어가 정확히 포함되지 않더라도 의미가 비슷한 문서를 찾는 검색입니다.

예:

```
질문:
잘못 보낸 돈을 돌려받으려면?

문서:
착오송금 반환지원 신청 절차
```

`착오송금`이라는 단어가 질문에 없어도 의미가 비슷하면 높은 점수를 받을 수 있습니다.

### 현재 처리 방식

문서 임베딩:

```
제목 + 소제목 + 본문
→ HCX bge-m3 임베딩
→ Dense Structured V2 JSONL 캐시에 저장
```

질문 임베딩:

```
검색용 독립질의
→ HCX bge-m3 임베딩
```

질문을 문서처럼 제목·소제목 구조로 바꾸지는 않습니다. 질문은 자연어 그대로 임베딩합니다.

질문 벡터와 모든 문서 벡터는 길이를 1로 정규화한 뒤 다음처럼 계산합니다.

```
Dense 점수 = 문서 벡터 · 질문 벡터
```

양쪽 벡터가 정규화되어 있으므로 사실상 Cosine Similarity입니다.

최종적으로 Dense 점수가 높은 문서 20개를 선택합니다.

### Dense Structured V2를 사용하는 이유

- 사용자의 다양한 표현을 의미적으로 대응
- `잘못 보낸 돈`과 `착오송금` 같은 표현 차이를 보완
- 제목과 소제목을 본문과 함께 사용하여 문서 주제를 강화
- 긴 본문 안에서 업무명이 약해지는 문제를 완화

## 4. BM25 Nori-none 검색

### BM25란?

질문에 들어 있는 단어가 문서에 얼마나 중요하게 등장하는지를 계산하는 전통적인 키워드 검색입니다.

Dense가 의미를 찾는다면, BM25는 정확한 용어를 찾는 데 강합니다.

예:

```
예금보험금
파산배당금
부채증명원
지급대행점
착오송금 수취인
```

이런 고유한 제도명이나 법률 용어는 BM25가 효과적입니다.

### Nori-none이란?

Nori는 Elasticsearch의 한국어 형태소 분석기입니다.

현재 설정은 다음과 같습니다.

```
nori_tokenizer
decompound_mode = none
```

`none`은 복합명사를 지나치게 분해하지 않는 설정입니다.

예를 들어 `예금자보호제도`를 작은 단어로 과도하게 쪼개면 `예금`, `보호`, `제도`처럼 일반적인 단어의 영향이 커질 수 있습니다. 현재는 복합어 형태를 최대한 유지하여 정확한 업무 용어 검색을 강화합니다.

### 현재 BM25 설정

```
k1 = 1.2
b  = 0.75
```

문서 필드는 Dense와 동일하게 다음 내용을 사용합니다.

```
제목 + 소제목 + 본문
```

BM25에서도 검색 질의마다 상위 20개를 가져옵니다.

## 5. Dense와 BM25의 7:3 Min-Max 결합

Dense 점수와 BM25 점수는 단위와 범위가 다릅니다.

예:

```
Dense 점수: 0.78, 0.74, 0.68
BM25 점수: 18.2, 12.7, 5.3
```

이를 바로 더하면 숫자가 큰 BM25가 과도하게 영향을 미칩니다. 따라서 각 검색 결과의 점수를 0~1 범위로 정규화합니다.

```
정규화 점수 = (현재 점수 - 최솟값) / (최댓값 - 최솟값)
```

그다음 다음 수식으로 합칩니다.

```
Hybrid 점수
= Dense 정규화 점수 × 0.7
+ BM25 정규화 점수 × 0.3
```

예:

| 청크 | Dense 정규화 | BM25 정규화 | 최종 점수 |
| --- | --- | --- | --- |
| A | 0.90 | 0.50 | 0.78 |
| B | 0.60 | 1.00 | 0.72 |
| C | 0.70 | 0.30 | 0.58 |

최종적으로 Hybrid 점수가 높은 20개를 다음 단계로 넘깁니다.

### 7:3을 사용하는 이유

Dense 검색을 중심으로 유지하면서 BM25의 정확한 용어 매칭을 보완하기 위한 비율입니다.

```
Dense 70% → 의미 검색 중심
BM25 30% → 고유 업무명·법률용어 보완
```

## 6. 복수 검색 질의의 가중 RRF 결합

현재 시스템에는 두 종류의 결합이 존재합니다.

| 결합 대상 | 사용 방식 |
| --- | --- |
| Dense와 BM25 | 7:3 Min-Max |
| 원문과 분해질의 | 가중 RRF, K=10 |

이 둘을 혼동하면 안 됩니다.

### 단일질의

검색계획이 하나라면 RRF를 적용해도 순위가 사실상 그대로 유지됩니다.

```
검색 질의 1개
→ Hybrid Top-20
→ 그대로 통합 후보 Top-20
```

### 교차업무 복합질의

검색계획이 여러 개라면 각 질의별 Hybrid Top-20을 만든 뒤 가중 RRF로 합칩니다.

현재 공식은 다음과 같습니다.

```
통합 점수
= Σ 검색질의 가중치 / (10 + 해당 질의에서의 순위)
```

예를 들어 어떤 청크가:

```
원문 검색에서 2위, 가중치 0.4
분해질의 A에서 1위, 가중치 0.3
```

라면:

```
0.4 / (10 + 2)
+ 0.3 / (10 + 1)
```

이런 방식으로 합산됩니다.

여러 검색 질의에서 반복해서 높은 순위를 받은 문서는 더 높은 통합 점수를 받습니다.

## 7. BAAI CrossEncoder Reranker

### Reranker란?

Dense와 BM25는 전체 문서에서 빠르게 후보를 찾는 역할을 합니다. Reranker는 이미 찾은 후보 20개를 대상으로 질문과 문서를 함께 읽고 관련성을 다시 판단합니다.

현재 모델은 다음과 같습니다.

```
BAAI/bge-reranker-v2-m3
```

### 입력 방식

각 후보마다 다음 쌍을 만듭니다.

```
[검색용 원질의, 후보 문서]
```

후보 문서는 다음 내용을 사용합니다.

```
제목 + 소제목 + 본문 앞부분
```

코드에서 문서는 우선 최대 4,000자로 제한되고, 모델 입력 단계에서 최대 512토큰으로 제한됩니다.

### 교차업무 복합질의에서의 기준 질문

분해질의가 여러 개 있어도 Reranker는 최종적으로 원문 앵커 질의를 기준으로 재정렬합니다.

```
원문 0.4
분해질의 A 0.3
분해질의 B 0.3
        ↓
RRF로 후보 20개 통합
        ↓
원문 전체 질문으로 Rerank
```

이렇게 하는 이유는 분해질의 하나에만 지나치게 맞는 문서가 최종 상위권을 독점하는 것을 막고, 사용자 질문 전체와 관련된 문서를 우선하기 위해서입니다.

### 최종 결과

```
Hybrid·RRF 통합 후보 20개
→ BAAI Reranker
→ 최종 Child Top-5
```

BAAI Reranker는 로컬에서 실행되므로 HCX API 호출량에는 포함되지 않습니다. 다만 GPU가 없으면 매우 느려질 수 있습니다.

## 8. Parent-Child8192 확장

### Child란?

실제 검색 순위를 결정하는 작은 청크입니다.

예:

```
DA-001_chunk_003
제목: 채무조정제도
소제목: 신청자격 및 구비서류
```

작은 청크는 특정 질문과의 관련성을 정확하게 계산하기 좋습니다.

### Parent란?

해당 Child가 포함된 전체 문서 또는 상위 문서 단위입니다.

예:

```
Parent: DA-001
Child:
- DA-001_chunk_000
- DA-001_chunk_001
- DA-001_chunk_002
- DA-001_chunk_003
```

### 현재 동작 방식

```
BAAI가 Child Top-5 선택
        ↓
각 Child의 Parent 확인
        ↓
매칭된 Child는 반드시 포함
        ↓
매칭 Child와 가까운 sibling 청크부터 추가
        ↓
Parent당 최대 8,192자까지 확장
```

여기서 `8,192`는 토큰이 아니라 문자 수입니다.

### 가장 중요한 특징

Parent-Child는 검색 순위를 바꾸지 않습니다.

```
검색 순위 결정: Child
답변 문맥 확장: Parent
```

따라서:

- Reranker 1위 Child는 Parent 확장 후에도 1위
- Parent 문서 전체 점수로 다시 정렬하지 않음
- Parent-Child는 검색 정확도보다 답변 근거 완전성을 보완

즉, 정확한 청크를 찾는 것은 Child가 담당하고, 앞뒤 조건·예외·절차를 제공하는 것은 Parent가 담당합니다.

### 같은 Parent가 여러 번 나온 경우

Top-5에 같은 Parent의 Child가 여러 개 포함되면 답변 B의 Evidence Pack에서는 Parent 단위로 묶습니다.

```
DA-001_chunk_002
DA-001_chunk_003
        ↓
Parent DA-001의 Evidence 하나로 통합
```

이를 통해 같은 문서 본문과 URL이 반복되는 것을 줄입니다.

## 9. 검색 결과의 최종 형태

최종 검색 결과는 다음 정보를 유지합니다.

| 필드 | 의미 |
| --- | --- |
| `rank` | Reranker 최종 순위 |
| `chunk_id` | 검색에 직접 매칭된 Child |
| `parent_doc_id` | 상위 Parent 문서 |
| `reranker_score` | BAAI 관련성 점수 |
| `pre_rerank_rank` | Reranker 적용 전 순위 |
| `dense_rank` | Dense 검색 순위 |
| `bm25_rank` | BM25 검색 순위 |
| `minmax_score` | Dense·BM25 7:3 결합 점수 |
| `matched_queries` | 어떤 원문·분해질의에서 검색됐는지 |
| `parent_context_chunk_ids` | 답변에 확장된 sibling 청크 |
| `source_url` | 공식 출처 URL |

이 결과가 다음 단계인 Basic Evidence Pack 생성으로 넘어갑니다.

## 10. 단계별 지연시간 측정

현재 검색 시스템은 다음 단계를 각각 측정합니다.

```
질문 임베딩
Dense 행렬 계산
BM25 검색
Min-Max 결합
다중질의 RRF 결합
BAAI Reranker
Parent-Child8192
검색 전체 Wall
```

첨부 CSV의 RETRIEVE 5건에서 관측된 값은 다음과 같습니다.

| 단계 | 중앙값 | 범위 |
| --- | --- | --- |
| 검색 전체 | 1,784.8ms | 1,396.2~8,759.0ms |
| 질문 임베딩 | 806.8ms | 642.4~8,123.3ms |
| Dense 계산 | 0.4ms | 0.3~1.5ms |
| BM25 | 16.7ms | 13.1~77.7ms |
| BAAI Reranker | 616.5ms | 579.7~1,061.0ms |
| Parent-Child8192 | 1.7ms | 1.6~5.0ms |

이 결과에서 중요한 점은 다음과 같습니다.

### Dense 계산 자체는 매우 빠름

```
중앙값 약 0.4ms
```

문서 벡터가 이미 JSONL에 저장되어 있어 질문 벡터와 행렬 내적만 수행하기 때문입니다.

### Dense 단계가 느려 보이는 원인은 질문 임베딩 API

질문 임베딩은 일반적으로 약 `0.6~0.8초`였지만, 일부 실행에서는 `8.1초`까지 증가했습니다.

따라서 검색 지연의 변동 원인은 Dense 행렬 계산이 아니라 HCX 질문 임베딩 호출입니다.

### BAAI Reranker는 비교적 일정

현재 GPU 실행 결과에서는 대체로:

```
약 0.58~1.06초
```

였습니다.

이전에 관측했던 64초 수준은 CPU 실행 또는 모델 초기화 상태였을 가능성이 큽니다.

### Parent-Child 자체는 매우 빠름

Parent-Child 확장은 로컬 딕셔너리에서 sibling 청크를 선택하는 작업이므로 약 `1~5ms`입니다.

다만 확장된 긴 문맥을 답변 LLM이 읽는 시간은 별개입니다.

```
Parent-Child 처리시간: 짧음
확장 문맥을 HCX-005가 읽는 답변시간: 길어질 수 있음
```

## 현재 검색 시스템의 안전 정책

### Hard Filter 미사용

모든 검색계획은 다음과 같습니다.

```
business_filter.mode = NONE
```

질의분석이 업무를 잘못 판단하더라도 다른 업무 문서를 검색 대상에서 강제로 제거하지 않습니다.

### 빈 검색 질의 방지

RETRIEVE 경로에서는 다음을 검사합니다.

- 검색계획이 존재하는지
- 각 검색 문자열이 비어 있지 않은지
- 가중치 합이 1.0인지
- 후보 수와 Top-K가 유효한지

유효하지 않으면 검색을 실행하지 않고 오류를 발생시킵니다.

### 현재 Reranker 점수 하한은 없음

현재 코드는 Reranker 점수가 낮아도 상대적으로 높은 Top-5를 답변 시스템으로 전달합니다.

예를 들어 CSV의 마지막 질문은 Reranker 1위 점수가 약 `0.083`이었지만 검색 결과가 답변 단계로 전달되었습니다.

따라서 현재 역할 분담은 다음과 같습니다.

```
검색 시스템:
상대적으로 가장 관련 있는 Top-5를 반환

답변 시스템:
근거가 충분한지 판단하고, 불충분하면 확정적으로 답하지 않음
```

검색 단계에서 저점수 후보를 즉시 거부하는 `refusal threshold`는 현재 적용되어 있지 않습니다.

## 한 문장으로 정리

현재 검색 시스템은 다음과 같습니다.

> 의미 검색에 강한 Dense Structured V2와 정확한 용어 검색에 강한 BM25 Nori-none를 7:3으로 결합하고, 복합질의의 여러 검색 결과를 가중 RRF로 통합한 뒤, BAAI Reranker로 최종 Child Top-5를 선정하고, 해당 Child가 속한 Parent 문맥을 최대 8,192자까지 확장하여 답변 시스템에 전달하는 하이브리드 검색 구조입니다.
