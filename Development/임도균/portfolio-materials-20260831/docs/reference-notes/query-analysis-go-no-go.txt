있습니다. 질의분석을 완벽하게 만들기보다 **검색으로 넘어가기 위한 통과 기준**, 즉 `Go/No-Go Gate`를 정하면 됩니다.

결론부터 말하면:

> 현재 V2는 대부분의 기준을 이미 통과했습니다.
> 
> 
> 검색 연동 전에 반드시 해결해야 할 것은 `잘못된 OUT_OF_SCOPE 8건`입니다.
> 

나머지 오류는 검색 단계에서 보완할 수 있으므로 질의분석을 계속 무겁게 만들 필요는 없습니다.

## 1. 왜 모든 지표가 높을 필요는 없는가?

질의분석 결과 중에는 잘못 판단해도 복구 가능한 것과 복구하기 어려운 것이 있습니다.

| 오류 | 영향 | 복구 가능성 |
| --- | --- | --- |
| 업무를 잘못 분류했지만 전체 검색 실행 | 검색 품질이 조금 낮아짐 | 높음 |
| 추가질문을 놓치고 먼저 검색 | 검색 후 다시 확인 가능 | 높음 |
| 불필요한 후검사 표시 | 검사 한 번 추가 | 높음 |
| 검색 질의를 조금 다르게 작성 | Hybrid 검색으로 보완 가능 | 높음 |
| 정상 질문을 OOS로 차단 | 검색 자체를 실행하지 않음 | 매우 낮음 |
| 정상 질문을 DIRECT로 처리 | 검색하지 않고 엉뚱한 응답 | 매우 낮음 |
| 잘못된 업무 Hard Filter | 정답 청크를 검색 대상에서 제외 | 낮음 |

따라서 질의분석에서 완벽해야 하는 것은 전체 정확도가 아니라 **검색을 차단하는 치명적인 오류**입니다.

## 2. 검색 연동 진입 기준

### 반드시 통과해야 하는 Hard Gate

| 지표 | 권장 통과 기준 | 이유 |
| --- | --- | --- |
| 실행 성공률 | 99.5% 이상 | 분석 실패로 질문이 유실되면 안 됨 |
| 검색 질의 생성 유효율 | 99% 이상 | RETRIEVE인데 검색어가 없는 경우 방지 |
| 정상 질문의 잘못된 OOS (out of scope) | 0건 | 검색 자체가 차단됨 |
| 정상 질문의 잘못된 DIRECT | 0건 | 검색 없이 잘못 종료됨 |
| 잘못된 Hard Filter | 0건 | 정답 업무가 검색 대상에서 제거됨 |
| 검색 불가능 질문의 추가질문 Precision | 95% 이상 | 불필요한 되묻기 방지 |

### 검색 불가능 질문의 추가질문 Precision ?

표현이 조금 어렵습니다. 더 쉽게 바꾸면:

챗봇이 검색을 멈추고 추가질문한 것 중, 정말 검색 전에 물어봐야 했던 비율

입니다.

지표 이름도 다음처럼 바꾸는 게 명확합니다.

```
검색 전 추가질문 정밀도
pre_retrieval_clarify_precision
```

## 1. 검색 불가능 질문이란?

현재 질문만으로는 어떤 업무를 검색해야 하는지 알 수 없는 질문입니다.

예를 들어:

```
신청 서류가 무엇인가요?
```

어떤 업무인지 없습니다.

- 착오송금 신청 서류
- 예금보험금 신청 서류
- 미수령금 신청 서류
- 채무조정 신청 서류

중 무엇을 검색해야 하는지 알 수 없습니다.

따라서 검색하기 전에 물어봐야 합니다.

```
어떤 제도나 업무의 신청 서류를 확인하고 싶으신가요?
```

이것이 `검색 전 추가질문이 필요한 질문`입니다.

## 2. 검색 가능한 질문

다음 질문은 업무가 명확합니다.

```
착오송금 반환지원 신청 서류는 무엇인가요?
```

바로 검색할 수 있습니다.

```
업무 = 착오송금 반환 신청
검색어 = 착오송금 반환지원 신청 서류
```

따라서 여기서 챗봇이 다음처럼 되묻는다면 불필요한 추가질문입니다.

```
어떤 업무의 신청 서류를 확인하고 싶으신가요?
```

## 3. 개인 조건이 없지만 검색은 가능한 질문

다음 질문도 검색 자체는 가능합니다.

```
제 신청 유형에 맞는 착오송금 신청 서류는 무엇인가요?
```

현재 본인·대리인·상속인 여부는 없지만:

```
착오송금 신청 유형별 서류
```

를 먼저 검색할 수 있습니다.

따라서 검색 전에 무조건 추가질문할 필요는 없습니다.

```
먼저 검색
→ 본인·대리인·상속인별 서류가 다름을 확인
→ 필요하면 검색 후 추가질문
```

## 4. Precision 계산 방법

예를 들어 챗봇이 20개 질문에서 검색을 멈추고 추가질문했다고 가정하겠습니다.

검수 결과:

- 정말 검색 전에 추가질문이 필요했던 질문: 18개
- 사실은 바로 검색할 수 있었던 질문: 2개

그러면:

```
검색 전 추가질문 Precision
= 올바른 검색 전 추가질문 18개
  ÷ 챗봇이 검색 전 추가질문한 20개

= 90%
```

쉽게 말하면:

> 챗봇이 사용자에게 되물었을 때 그 질문이 얼마나 타당했는가?
> 

## 5. Precision이 낮으면 발생하는 문제

사용자:

```
착오송금 반환지원 신청 기한은 언제인가요?
```

챗봇:

```
어떤 업무에 대해 문의하시는 건가요?
```

이미 업무가 명확한데 다시 물었습니다.

이런 경우가 많으면 Precision이 낮아집니다.

사용자는 다음처럼 느낍니다.

```
질문을 정확히 했는데 왜 또 물어보지?
```

그래서 검색 전 추가질문 Precision은 높아야 합니다.

권장 기준은:

```
95% 이상
```

입니다.

## 6. Recall은 무엇인가?

Recall은 반대쪽을 봅니다.

> 정말 검색 전에 물어봐야 하는 질문 중 챗봇이 얼마나 찾아냈는가?
> 

실제로 검색 전 추가질문이 필요한 질문이 25개인데, 챗봇이 그중 18개만 잡았다면:

```
검색 전 추가질문 Recall
= 18 ÷ 25
= 72%
```

나머지 7개는 추가질문하지 않고 검색으로 보냈습니다.

## 7. Precision과 Recall 차이

| 지표 | 쉽게 말하면 |
| --- | --- |
| 검색 전 추가질문 Precision | 되물은 것이 정말 필요했는가? |
| 검색 전 추가질문 Recall | 되물어야 할 질문을 놓치지 않았는가? |

### Precision 오류

```
검색할 수 있는데 불필요하게 되물음
```

### Recall 오류

```
검색하기 어려운데 추가질문하지 않고 검색함
```

## 8. 어떤 지표가 더 중요한가?

검색 전 추가질문에서는 Precision을 우선하는 것이 좋습니다.

왜냐하면 검색 가능한 질문까지 막으면 사용자 경험이 나빠지기 때문입니다.

```
조금 애매하지만 검색 가능
→ 우선 검색
→ 검색 후 필요하면 추가질문
```

따라서 권장 방향은:

```
검색 전 추가질문 Precision ≥ 95%
검색 전 추가질문 Recall ≥ 85~90%
```

입니다.

다만 Recall이 조금 낮더라도 검색 후 추가질문 단계에서 보완할 수 있습니다.

| --- | --- | --- |

## 10. 현재 평가데이터셋의 문제

현재 Gold에는 다음 값만 있습니다.

```
CLARIFY
```

하지만 `CLARIFY` 안에는 두 종류가 섞여 있습니다.

```
검색 전에 반드시 추가질문
검색 후 조건을 보고 추가질문
```

따라서 정확한 평가를 하려면 다음 칼럼이 필요합니다.

```
clarification_stage_gold
```

값은 다음과 같습니다.

| 값 | 의미 |
| --- | --- |
| `PRE_RETRIEVAL` | 검색 자체가 어려워 검색 전에 추가질문 |
| `POST_RETRIEVAL` | 검색은 가능하지만 최종 답변 전에 추가질문 |
| `NONE` | 추가질문 필요 없음 |

예를 들어:

| 질문 | clarification_stage_gold |
| --- | --- |
| 신청 서류가 무엇인가요? | `PRE_RETRIEVAL` |
| 제 유형에 맞는 착오송금 서류는? | `POST_RETRIEVAL` |
| 착오송금 신청 기한은? | `NONE` |

## 핵심 정리

`검색 불가능 질문의 추가질문 Precision`이라는 표현은:

> 챗봇이 검색 전에 추가질문한 질문 중 실제로 검색 전에 물어봐야 했던 질문의 비율
> 

입니다.

더 이해하기 쉬운 이름은 다음입니다.

```
검색 전 추가질문 정밀도
```

그리고 현재 평가데이터셋의 `clarify_precision`과 완전히 같은 지표는 아닙니다. 정확히 측정하려면 Gold 추가질문을 `검색 전`과 `검색 후`로 나눠야 합니다.

여기에서 `잘못된 OOS 0건`이 가장 중요한 조건입니다.

### 완벽하지 않아도 되는 Soft Gate

| 지표 | 권장 통과 기준 | 현재 V2 |
| --- | --- | --- |
| 라우팅 정확도 | 75% 이상 | 78.89% |
| 라우팅 Macro F1 | 70% 이상 | 73.78% |
| 업무 분류 Micro F1 | 85% 이상 | 90.00% |
| 검색 전 추가질문 Precision | 95% 이상 | 100% |
| 검색 전·후 추가질문 커버리지 | 85% 이상 | 85% |
| LLM 호출률 | 60% 이하 | 53.70% |
| 질의분석 평균시간 | 1.5초 이하 | 1.09초 |
| 질의분석 P95 | 2.5초 이하 | 2.11초 |
| 실행 성공률 | 99.5% 이상 | 100% |
| 검색 질의 유효율 | 99% 이상 | 100% |

현재 V2는 Soft Gate를 전부 통과합니다.

현재 유일한 Hard Gate 실패는 다음입니다.

```
잘못된 OUT_OF_SCOPE: 8건
```

## 3. OOS를 완벽하게 분류하려고 하면 무거워질 수 있음

맞습니다. OOS 정확도를 높이려고 다음을 추가하면 질의분석이 다시 무거워집니다.

```
OOS 판단용 LLM 호출
→ 업무 검증용 LLM 호출
→ 신뢰도 재판단
→ 검색 여부 결정
```

이렇게 하지 않고 더 간단한 방법이 있습니다.

> 질의분석 단계에서는 OOS를 보수적으로 사용하고, 애매하면 일단 검색한다.
> 

## 4. OOS는 Fail-Open 방식으로 변경

현재 구조는 LLM이 `OUT_OF_SCOPE`를 반환하면 검색하지 않을 수 있습니다.

이를 다음과 같이 바꾸는 것이 좋습니다.

```
```mermaid
flowchart TD
    A["질의분석 결과"] --> B{"OUT_OF_SCOPE인가?"}

    B -- "아니요" --> C["기존 경로 진행"]
    B -- "예" --> D{"명백한 범위 밖 규칙에 일치하는가?"}

    D -- "예" --> E["OUT_OF_SCOPE 확정"]
    D -- "아니요" --> F["RETRIEVE로 보정"]

    F --> G["업무 Hard Filter 사용 안 함"]
    G --> H["전체 범위 검색"]
```
```

명백한 OOS만 검색 전에 차단합니다.

```
오늘 날씨
주식 추천
맛집 추천
로또 번호
번역 요청
코딩 요청
```

그 외 LLM이 OOS라고 판단한 질문은 다음처럼 처리합니다.

```
route_type = RETRIEVE
business_filter_mode = NONE
search_queries = 원문 질문
```

그러면 다음과 같은 새로운 업무 표현이 사전에 없어도 검색됩니다.

```
상속인 금융거래 조회
지급명령
강제집행
면책 불허가
파산선고의 불이익
```

### 장점

- OOS 확인용 LLM 추가 호출이 없음
- 새로운 KDIC 표현을 놓쳐도 검색 가능
- 정상 질문이 검색 전에 차단되지 않음
- 업무를 모르면 Hard Filter 없이 전체 검색 가능

### 단점

범위 밖 질문 일부가 검색 시스템까지 넘어갑니다.

하지만 이것은 치명적이지 않습니다.

```
날씨 질문이 검색으로 넘어감
→ 관련 근거 없음
→ 검색 후 OUT_OF_SCOPE 또는 근거 부족
```

비용은 조금 들지만 정상 질문을 차단하는 것보다 안전합니다.

## 5. OOS Recall보다 Precision을 중요하게 봐야 함

OOS 평가에서는 두 오류의 중요도가 다릅니다.

### 실제 OOS를 RETRIEVE로 보냄

```
오늘 날씨가 어때요?
→ RETRIEVE
```

불필요한 검색이 한 번 발생하지만, 검색 후 범위 밖으로 처리할 수 있습니다.

### 정상 질문을 OOS로 보냄

```
파산선고를 받으면 곧바로 면책되나요?
→ OUT_OF_SCOPE
```

정답 근거를 검색할 기회 자체가 사라집니다.

따라서 목표는 다음처럼 잡는 게 좋습니다.

```
OOS Recall: 90% 이상이면 충분
OOS Precision: 95% 이상
정상 질문 False OOS: 평가셋에서 0건
```

더 간단하게는 다음 한 줄만 Hard Gate로 잡아도 됩니다.

> KDIC 정상 질문을 OOS로 차단한 건수가 0건이어야 검색 연동 통과.
> 

## 6. 업무 분류도 완벽할 필요가 없음

업무 분류 F1이 90%라면 충분히 검색으로 넘어갈 수 있습니다.

중요한 것은 신뢰도에 따른 필터 정책입니다.

```
업무가 명시적으로 확인됨
→ Hard Filter

LLM만 업무를 추정함
→ Soft Filter

업무가 불확실함
→ Filter 없음
```

```
```mermaid
flowchart TD
    A["업무 분류 결과"] --> B{"업무가 질문에 명시돼 있는가?"}

    B -- "예" --> C["Hard Filter"]
    B -- "아니요" --> D{"업무 후보가 있는가?"}

    D -- "예" --> E["Soft Boost"]
    D -- "아니요" --> F["전체 검색"]
```
```

이렇게 하면 업무를 틀려도 검색 결과가 완전히 사라지지 않습니다.

따라서 업무 분류 정확도를 95~99%까지 올리려고 LLM을 추가 호출할 필요가 없습니다.

## 7. 추가질문 지표도 검색 전 Recall을 높일 필요 없음

검색 전 추가질문 Recall을 90%까지 올리려고 하면 다음 문제가 발생합니다.

```
조금만 모호해도 CLARIFY
→ 검색 전에 계속 되물음
→ 사용자 경험 저하
→ 검색 가능한 질문까지 차단
```

질의분석에서는 다음만 잡으면 됩니다.

### 검색 전 반드시 추가질문

```
신청 서류가 무엇인가요?
신청 기한이 언제인가요?
어디에서 조회하나요?
```

업무 자체를 알 수 없는 질문입니다.

### 검색 후 추가질문

```
제 신청 유형에 맞는 서류는?
이 상품도 보호되나요?
제 경우 얼마까지 보호되나요?
```

업무 검색은 가능하므로 먼저 검색합니다.

따라서 지표도 두 개로 나누는 게 좋습니다.

| 지표 | 권장 기준 |
| --- | --- |
| 검색 불가능 질문의 사전 CLARIFY Precision | 95% 이상 |
| 검색 불가능 질문의 사전 CLARIFY Recall | 90% 이상 |
| 검색 후 추가질문 후보 커버리지 | 85% 이상 |
| Gold 전체 기준 사전 CLARIFY Recall | 참고용 |

현재 `18.33%`인 전체 사전 CLARIFY Recall은 검색 연동을 막을 지표가 아닙니다.

다만 `검색 자체가 불가능한 질문`만 별도 묶어서 Recall을 계산해야 합니다. 현재 평가데이터셋에서는 이 구분이 명확하지 않으므로 다음 칼럼을 추가하면 됩니다.

```
clarification_stage_gold
```

값은 다음 두 개면 충분합니다.

```
PRE_RETRIEVAL
POST_RETRIEVAL
```

다음 표를 프로젝트의 공식 기준으로 사용하는 것을 권장합니다.

| 구분 | 지표 | 통과 기준 | 현재 V2 | 상태 |
| --- | --- | --- | --- | --- |
| 안전성 | 실행 성공률 | ≥99.5% | 100% | 통과 |
| 안전성 | 잘못된 OOS | 0건 | 8건 | 미통과 |
| 안전성 | 잘못된 DIRECT | 0건 | 0건 | 통과 |
| 검색 준비 | 검색 질의 유효율 | ≥99% | 100% | 통과 |

```

## 9. 지금 해야 할 최소 작업

질의분석을 계속 고도화할 필요는 없습니다. 다음만 하면 됩니다.

### 1단계: OOS 종료 조건 변경

```
정확한 규칙으로 잡힌 명백한 OOS
→ OUT_OF_SCOPE

LLM이 OOS라고 판단했지만 명백하지 않음
→ RETRIEVE + Filter NONE
```

이렇게 하면 잘못된 OOS 8건을 사전 추가 없이 검색으로 보낼 수 있습니다.

### 2단계: Hard Filter 안전성 확인

평가데이터셋에서 다음을 측정합니다.

```
Gold 업무가 검색 대상에서 제외된 질문 수
```

통과 기준은 0건입니다.

자신 없으면 전부 Soft Filter로 바꿔도 됩니다.

### 3단계: 270건 한 번 재평가

다음 세 값만 확인합니다.

```
False OOS = 0
False DIRECT = 0
Hard Filter Exclusion = 0
```

이 세 가지가 통과하면 질의분석 버전을 동결합니다.

```
Query Analyzer V2.1 Freeze
```

그 이후에는 질의분석 정확도를 더 올리려고 시간을 쓰기보다 검색 성능 평가로 넘어갑니다.

## 10. 검색 단계로 넘어간 후 볼 지표

질의분석이 완벽하더라도 검색이 정답 근거를 못 찾으면 의미가 없습니다.

다음 단계에서는 다음 지표를 봐야 합니다.

| 검색 지표 | 초기 권장 기준 |
| --- | --- |
| 검색 실행 성공률 | ≥99.5% |
| Gold Evidence Recall@20 | ≥95% |
| Gold Evidence Recall@5 | ≥85% |
| 업무 Hard Filter로 인한 정답 누락 | 0건 |
| 빈 검색 결과율 | ≤1% |
| 질의분석+검색 P95 | ≤4초 |
| 복합질의 하위 요구 커버리지 | ≥85% |

## 최종 결론

질의분석에서 90% 이상의 모든 지표를 요구할 필요는 없습니다.

검색으로 넘어가기 위한 핵심 기준은 다음 5개면 충분합니다.

```
1. 실행 성공률 99.5% 이상
2. 검색 질의 유효율 99% 이상
3. 정상 질문 False OOS 0건
4. 잘못된 Hard Filter 0건
5. 질의분석 P95 2.5초 이하
```

현재 V2에서는 1, 2, 5는 이미 통과했습니다.

따라서:

> OOS를 Fail-Open 방식으로 바꾸고 Hard Filter 안전성만 확인한 뒤, 질의분석을 동결하고 검색 시스템 평가로 넘어가는 것을 권장합니다.
