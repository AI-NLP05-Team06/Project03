────────────────────────────────────────
슬라이드 4. 근거 기반 AI 챗봇 구축
예상 시간: 50초
────────────────────────────────────────

기존 대외 챗봇인 예솜24는 미리 정의된 키워드와 카드형 답변에는 강하지만, 사용자가 표현을 바꾸거나 복합적인 자연어 질문을 하면 대응하기 어렵다는 한계가 있었습니다.

특히 예금보험 업무는 금액, 기간, 대상 조건처럼 세부 조건이 많습니다. 따라서 근거 없이 답변을 단정하면 잘못된 안내나 민원으로 이어질 위험이 있습니다.

저희는 이 문제를 해결하기 위해 6개 업무의 자연어 질문을 검색하고, 답변마다 공식 URL과 브레드크럼을 제시하는 RAG 챗봇을 목표로 정했습니다.

또 민원성 질문에는 단순 설명만 제공하는 것이 아니라 절차, 필요 서류, 실제 신청 페이지까지 이어지는 흐름을 설계했습니다.


────────────────────────────────────────
슬라이드 5. 프로젝트 1 데이터에서 프로젝트 2 서비스로
예상 시간: 50초
────────────────────────────────────────

프로젝트 1에서는 6개 업무 도메인의 공식 웹페이지를 수집하고, HTML을 Markdown으로 정제한 뒤 계층형 메타데이터와 청크를 만들었습니다.

이 과정에서 업무를 구분하는 business_function, 상위 문서를 연결하는 parent_doc_id, 그리고 출처 URL과 첨부파일 정보를 함께 저장했습니다.

프로젝트 2에서는 이 산출물을 새로 만드는 것이 아니라 실제 서비스 기능으로 전환했습니다.

business_function은 업무별 검색 범위를 제한하는 데 사용하고, parent_doc_id는 답변에 필요한 상위 문맥을 확장하는 데 사용합니다.

또 source URL과 breadcrumb는 출처 표시로, attachments 메타데이터는 민원 서류 다운로드 안내로 연결하도록 설계했습니다.

────────────────────────────────────────
슬라이드 8. 협업 구조와 산출물 연결
예상 시간: 35초
────────────────────────────────────────

업무는 데이터 기반, 서비스 설계, 평가와 검수, 발표와 시연 영역으로 구분했습니다.

다만 각 담당자가 결과를 따로 완성하는 방식이 아니라, 앞 단계의 산출물이 다음 단계의 입력값이 되도록 연결했습니다.

예를 들어 데이터 담당자가 만든 청크와 메타데이터를 서비스 설계와 평가 담당자가 직접 확인했고, 예상질문과 Gold 근거는 프로토타입 화면과 시연 시나리오로 이어졌습니다.

CSV, HTML 검수 도구, 스크린샷을 공통 산출물로 공유하고 교차 검수해 팀원 간 이해 차이를 줄이려 했습니다.

슬라이드 9. 프로젝트 수행 과정
예상 시간: 35초
────────────────────────────────────────

전체 과정은 여섯 단계로 진행했습니다.

먼저 프로젝트 1 산출물과 기존 챗봇의 한계를 분석하고, FAQ와 업무·의도 선택 방식 등 사용자 흐름을 정했습니다.

그다음 업무 분류, 필터 검색, 답변과 출처로 이어지는 파이프라인을 설계했습니다.

이 구조를 평가할 수 있도록 질문, 의도, Gold 근거와 필수응답요소를 포함한 평가 데이터셋을 만들었습니다.

마지막에는 수기 검수와 API 보조 검토, HTML 청크 검수 도구를 활용해 정답 근거를 확인하고 시연을 준비했습니다.


────────────────────────────────────────
슬라이드 10. 전체 파이프라인 설계
예상 시간: 45초
────────────────────────────────────────

파이프라인은 데이터 준비부터 답변 평가까지 여섯 단계로 구성했습니다.

공식 웹페이지를 수집해 Markdown으로 정제하고, 총 427개의 작은 Child 청크로 나눴습니다.

각 청크는 bge-m3 모델을 이용해 1,024차원 벡터로 임베딩합니다.

사용자 질문이 들어오면 먼저 업무와 의도, 필요한 추가 조건을 파악하고, 해당 업무 범위 안에서만 근거를 검색합니다.

검색된 청크와 상위 문맥을 LLM에 제공해 답변을 생성하고, 마지막에는 URL과 브레드크럼을 표시합니다.

이 결과를 Gold 테스트셋과 비교해 검색과 답변 품질을 개선하는 구조입니다.


────────────────────────────────────────
슬라이드 11. UI/UX 의논
예상 시간: 40초
────────────────────────────────────────

UI와 UX는 세 가지 관점에서 논의했습니다.

첫째, 사용자가 무엇을 질문해야 할지 고민하지 않도록 첫 화면에 전체 FAQ TOP 5를 제시합니다.

둘째, 업무와 질문 의도를 반드시 선택하도록 강제하지 않고 기본적으로는 챗봇이 자동 분류하도록 했습니다. 다만 사용자가 원하는 경우 버튼으로 결과를 직접 보정할 수 있습니다.

셋째, 추가 조건이 필요한 질문에는 자유 입력부터 요구하기보다 선택 가능한 버튼을 먼저 제공합니다.

최종적으로 FAQ 또는 자유 질문, 자동 분류, 필요 시 추가 질문, 근거 기반 답변과 출처로 이어지는 혼합형 흐름을 선택했습니다.


────────────────────────────────────────
슬라이드 12. 서비스 측면의 시스템 구축
예상 시간: 40초
────────────────────────────────────────

서비스는 사용자 접점, 서비스 처리, RAG 처리, 데이터와 평가의 네 계층으로 정리했습니다.

사용자 화면에서는 FAQ와 자유 질문, 설명 수준, 업무와 의도를 선택할 수 있습니다.

서비스 계층에서는 세션 상태와 요청 형식, LLM API와 응답 포맷을 관리합니다.

RAG 계층에서는 업무와 의도를 분류하고, 업무 필터를 적용한 뒤 근거 답변과 출처를 검증합니다.

향후 실제 서비스로 확장할 경우에는 IP나 세션 단위 사용량 제한, 동일 질문 캐시, 실패 로그와 개인정보 입력 안내도 추가할 계획입니다.


────────────────────────────────────────
슬라이드 13. 평가 데이터셋 프레임
예상 시간: 45초
────────────────────────────────────────

평가 데이터셋은 단순한 예상질문 목록이 아닙니다.

하나의 질문을 기준으로 질문 정보, 의도 정답, 검색 정답, 답변 정답을 함께 연결했습니다.

질문 정보에는 질문 ID, 중요도, 복잡도와 질문유형이 들어갑니다.

의도 정답에는 업무 라벨과 INFORMATION 또는 ACTION 같은 의도 그룹, 상세의도와 사용자 역할을 기록합니다.

검색 정답에는 찾아야 할 문서, 섹션, 청크와 URL을 Gold 값으로 지정합니다.

답변 정답에는 반드시 포함해야 할 내용, 추가 질문 필요 여부와 응답정책을 기록합니다.

이 구조를 통해 오류가 발생했을 때 업무 분류, 검색, 답변 중 어느 단계를 개선해야 하는지 구분할 수 있습니다.


────────────────────────────────────────
슬라이드 14. 평가 데이터 검수
예상 시간: 45초
────────────────────────────────────────

검수는 수기 검토와 API 보조 검토의 역할을 분리했습니다.

API는 라벨 초안 작성, 문장 정리, 누락이나 형식 불일치 후보를 찾는 데 활용했습니다.

하지만 실제 업무와 의도가 맞는지, Gold 문서와 청크가 정확한지는 원문을 확인한 사람이 최종 승인했습니다.

검수 흐름은 질문 초안을 만든 뒤 API로 1차 라벨을 보조하고, 담당자가 원문과 Gold 근거를 확인한 다음 팀원이 교차 검수하는 방식입니다.

즉, API는 검수 속도와 일관성을 보조하지만 도메인 정답을 대신 결정하지 않도록 했습니다.

────────────────────────────────────────
슬라이드 16. 핵심 산출물과 달성 결과
예상 시간: 40초
────────────────────────────────────────

이번 프로젝트에서 완성한 핵심 산출물은 여섯 가지입니다.

프로젝트 1의 데이터 구조와 품질 이슈를 정리한 보고서, UI·UX 설계안, 챗봇 서비스와 검색·답변 구조, 전체 파이프라인, 평가 데이터셋, 그리고 시연 화면입니다.

데이터 측면에서는 427개 청크와 1,024차원 벡터, Parent-Child와 출처 연결 구조를 활용했습니다.

평가 데이터셋은 203행, 38개 필드로 구성했으며 143개의 질문 ID를 부여했습니다.

중요한 점은 개별 파일을 만드는 데서 끝나지 않고, 데이터부터 화면과 평가까지 하나의 서비스 흐름으로 연결했다는 것입니다.


────────────────────────────────────────
슬라이드 17. 첫 화면과 전체 FAQ TOP 5
예상 시간: 25초
────────────────────────────────────────

첫 화면에서는 사용자가 서비스의 목적과 질문 입력 위치를 바로 이해할 수 있도록 구성했습니다.

또 자주 묻는 질문 TOP 5를 먼저 제시해 사용자가 질문 문장을 직접 작성하지 않아도 원하는 질문을 바로 실행할 수 있습니다.

반복 질문은 FAQ 버튼으로 처리해 사용자의 입력 부담과 LLM 호출 비용을 함께 줄이는 효과도 기대할 수 있습니다.

슬라이드 18. 질문 의도 설정
예상 시간: 25초
────────────────────────────────────────

질문 의도는 기본적으로 챗봇이 문맥을 보고 자동 분류합니다.

따라서 사용자가 아무것도 선택하지 않아도 질문할 수 있습니다.

다만 정보 안내, 신청·처리, 현황 안내처럼 원하는 답변 방향이 명확한 경우에는 사용자가 직접 선택해 자동 분류 결과를 보정할 수 있도록 했습니다.


────────────────────────────────────────
슬라이드 19. 업무 분류
예상 시간: 25초
────────────────────────────────────────

업무는 예금자보호, 예금보험금, 고객 미수령금, 착오송금, 채무조정, 은닉재산의 6개로 구분했습니다.

업무를 선택하면 검색 범위를 해당 업무의 청크로 제한합니다.

예를 들어 여러 업무에 반복되는 ‘신청 기한’이나 ‘신청 방법’ 같은 표현 때문에 다른 업무의 근거가 섞이는 위험을 줄이기 위한 기능입니다.


────────────────────────────────────────
슬라이드 20. 설명 수준 설정
예상 시간: 20초
────────────────────────────────────────

같은 근거를 사용하더라도 사용자의 이해 수준에 따라 표현 방식을 선택할 수 있습니다.

쉬운 설명은 전문 용어를 풀고 핵심 절차 중심으로 안내합니다.

전문가 설명은 정확한 업무 용어와 조건, 예외 사항을 조금 더 상세하게 제공하도록 설계했습니다.


────────────────────────────────────────
슬라이드 21. 업무별 자주 묻는 질문
예상 시간: 20초
────────────────────────────────────────

전체 FAQ 외에도 업무별 FAQ TOP 5를 제공합니다.

사용자가 업무 탭을 선택하면 해당 업무에서 자주 묻는 대표 질문만 확인할 수 있습니다.

이를 통해 전체 범위에서 질문을 찾는 대신 관심 업무로 탐색 범위를 단계적으로 좁힐 수 있습니다.


────────────────────────────────────────
슬라이드 22. 답변 화면과 후속 질문
예상 시간: 30초
────────────────────────────────────────

답변 화면에서는 자연어 답변만 제시하지 않습니다.

답변 아래에서 사용한 공식 근거와 출처를 펼쳐 볼 수 있고, 원문 페이지에서도 내용을 다시 확인할 수 있습니다.

또 현재 질문과 관련해 이어서 많이 묻는 내용을 버튼으로 제공합니다.

즉, 직접 답변, 공식 근거 확인, 후속 질문으로 이어지는 구조를 통해 한 번의 답변에서 다음 탐색까지 연결했습니다.


────────────────────────────────────────
슬라이드 23. 평가 데이터셋과 품질평가 계획
예상 시간: 50초
────────────────────────────────────────

평가 데이터셋은 총 203행, 38개 필드로 구성했고, 143개의 질문 ID를 포함했습니다.

6개 업무의 일반 질문뿐 아니라 범위 밖 질문, 모호한 질문, 조건부 질문과 복합 질문도 포함했습니다.

질문마다 정답 문서, 섹션, 청크를 Gold 값으로 지정하고, 답변에 반드시 포함해야 할 요소와 응답정책도 기록했습니다.

검수 상태는 자동승인, 검토대기, 매핑 상태 등으로 구분해 관리했습니다.

다음 단계에서는 이 데이터셋을 이용해 정답 청크가 Top-K 안에 들어왔는지를 보는 Hit@K, 정답 순위를 보는 MRR, 답변 근거성과 업무 혼입률을 비교할 예정입니다.


────────────────────────────────────────
슬라이드 24. 기존 CSV 검수의 어려움
예상 시간: 35초
────────────────────────────────────────

평가 데이터셋을 만들면서 가장 시간이 많이 걸린 부분은 Gold 근거 검수였습니다.

기존 CSV에서는 질문 ID와 업무, URL, 질문유형이 가로로 길게 나열되어 있습니다.

정답 문서, 섹션, 청크도 서로 다른 열에 흩어져 있어 질문 하나를 검토할 때 화면을 좌우로 이동해야 했습니다.

또 실제 청크 원문은 별도의 JSONL 파일에서 찾아야 했기 때문에 잘못된 매핑이나 근거 누락을 빠르게 발견하기 어려웠습니다.


────────────────────────────────────────
슬라이드 25. Gold 청크 검수 도구
예상 시간: 40초
────────────────────────────────────────

이 문제를 줄이기 위해 질문별 Gold 청크를 한 화면에서 확인하는 HTML 검수 도구를 만들었습니다.

질문과 라벨, 현재 지정된 Gold 상태를 먼저 확인하고, 청크 ID를 누르면 실제 원문을 펼쳐 볼 수 있습니다.

기존 Gold가 부족한 경우에는 같은 문서뿐 아니라 전체 427개 청크에서 검색해 정답 근거를 추가할 수 있습니다.

반대로 잘못 지정된 청크는 제거할 수 있습니다.

이 도구를 통해 가로로 긴 CSV와 JSONL 파일을 번갈아 보던 검수 과정을 질문 단위의 화면으로 바꿨습니다.
