## 전체 파이프라인

```
1. 사용자 질문 입력
   ↓
2. 원문 보존 + 최소 정리
   ↓
3. 대화 상태 확인
   ↓
4. 현재 질문과 이전 업무의 관계 판정
   ├─ 독립적인 새 질문
   ├─ 이전 업무의 후속 질문
   ├─ 정정·제외·취소
   └─ 판단에 필요한 정보 부족
   ↓
5. 최종 경로 결정
   ├─ RETRIEVE
   ├─ CLARIFY
   ├─ OUT_OF_SCOPE
   └─ DIRECT_RESPONSE
   ↓
6. 업무 및 질의 유형 판정
   ├─ SINGLE
   ├─ SAME_BUSINESS_MULTI
   └─ CROSS_BUSINESS
   ↓
7. 교차업무 질의만 HCX-007 구조화 분해
   ↓
8. 분해 결과 검증
   ├─ 승인 → 원문 0.4 + 분해질의 총합 0.6
   └─ 거부·실패 → 원문 1.0 fallback
   ↓
9. 문맥 업무 보존 및 검색계획 안전성 검사
   ↓
10. 유효한 검색계획만 검색 시스템으로 전달
```

---

## 1. 사용자 질문 입력과 원문 보존

사용자가 입력한 질문은 먼저 원문 그대로 보존됩니다.

예:

```
사용자 원문:
신청 서류는 어떻게 돼?
```

이 원문은 다음 두 용도로 유지됩니다.

- 사용자 화면과 로그에 원래 질문을 표시
- 질의분석 또는 분해가 실패했을 때 원문 검색으로 복귀

따라서 LLM이나 규칙이 질문을 잘못 변형하더라도 원문을 잃지 않습니다.

---

## 2. 최소 정규화

정규화는 질문의 의미를 바꾸는 재작성이 아니라, 분석 가능한 형태로 정리하는 작업입니다.

현재 코드가 처리하는 항목은 다음과 같습니다.

| 처리 | 예시 | 목적 |
| --- | --- | --- |
| 공백 정리 | `신청   서류` → `신청 서류` | 패턴 매칭 안정화 |
| Unicode NFKC 통일 | 서로 다른 문자 표현 통일 | 문자열 비교 안정화 |
| 제어문자 제거 | 보이지 않는 특수문자 제거 | 오류 방지 |
| 과도한 반복문자 정리 | `뭐야?????` → `뭐야??` | 검색어 잡음 감소 |
| 확실한 오타 교정 | `예금보헝금` → `예금보험금` | 업무 탐지 보완 |
| 원문 보존 | 교정 전 질문 별도 유지 | 의미 변형 방지 |

엄밀히 말하면 현재 코드는 먼저 공백을 정리한 문장으로 멀티턴을 판정하고, 문맥이 결합된 독립질의를 V1.5 본체에 전달한 뒤 전체 최소 정규화를 다시 수행합니다.

---

## 3. 대화 상태 관리

현재 시스템은 직전 답변 문자열을 무조건 현재 질문에 붙이지 않습니다. 다음과 같은 구조화된 상태를 관리합니다.

| 상태 | 의미 |
| --- | --- |
| `active_businesses` | 현재 대화에서 활성화된 업무 |
| `excluded_businesses` | 사용자가 제외한 업무 |
| `actor_role` | 송금인·수취인 등 확인된 역할 |
| `pending_clarification` | 시스템이 되물었지만 아직 답하지 않은 항목 |
| `last_resolved_question` | 직전 검색에 사용한 독립질의 |

예를 들어 첫 질문이 다음이라면:

```
채무조정 신청하려면 어떻게 해야 하나요?
```

상태에는 다음과 같이 저장됩니다.

```
active_businesses = ["채무조정"]
```

그다음 질문이:

```
신청 서류는 어떻게 돼?
```

라면 질문 자체에 업무명이 없더라도 활성 업무가 하나이므로 다음과 같이 결합합니다.

```
채무조정 관련 신청 서류는 어떻게 돼?
```

CSV에서도 실제로 이렇게 처리되었습니다.

| 질문 | 검색용 독립질의 | 문맥 사용 |
| --- | --- | --- |
| 채무조정 신청하려면 어떻게 해야 하나요? | 원문 그대로 | False |
| 신청 서류는 어떻게 돼? | 채무조정 관련 신청 서류는 어떻게 돼? | True |

---

## 4. 현재 질문과 이전 문맥의 관계 판정

이 단계의 핵심 원칙은 다음과 같습니다.

> 현재 질문만으로 충분하면 이전 문맥을 사용하지 않고, 후속 질문이라는 근거가 명확할 때만 이전 업무를 결합한다.
> 

### 4-1. 독립적으로 완결된 새 질문

질문에 업무명과 의도가 모두 들어 있으면 이전 업무를 덮어씁니다.

```
이전 업무: 채무조정
현재 질문: 착오송금 반환지원은 누가 신청할 수 있나요?
```

처리:

```
문맥 판단: CURRENT_QUESTION_COMPLETE
문맥 사용: False
활성 업무: 착오송금 반환지원
검색 질의: 현재 질문 원문
```

이전 대화가 채무조정이었다고 해서 착오송금 질문에 채무조정을 섞지 않습니다.

### 4-2. 의도만 있는 후속 질문

현재 개선 버전은 다음과 같은 표현을 후속질의 의도로 탐지합니다.

- 신청·접수
- 서류·준비물
- 자격·대상
- 절차·방법
- 기간·기한
- 비용·수수료
- 조회·확인
- 금액·한도
- 예외·제외
- 취소·철회
- 본인·대리인·송금인·수취인
- 이유

업무명이 없고 후속 의도만 있지만 활성 업무가 정확히 하나라면 해당 업무를 붙입니다.

```
활성 업무: 채무조정
현재 질문: 필요한 준비물이 뭐야?

검색용 독립질의:
채무조정 관련 필요한 준비물이 뭐야?
```

이 과정에는 LLM을 사용하지 않습니다. 규칙으로 빠르게 처리합니다.

### 4-3. 활성 업무가 없는 후속 질문

```
현재 질문: 신청 서류는 어떻게 돼?
활성 업무: 없음
```

어떤 신청의 서류인지 알 수 없으므로 검색하지 않습니다.

```
최종 경로: CLARIFY
질문: 어떤 업무에 관한 질문인지 알려주세요.
```

### 4-4. 활성 업무가 둘 이상인 후속 질문

```
활성 업무:
- 고객 미수령금
- 착오송금 반환지원

현재 질문:
신청 서류는 어떻게 돼?
```

어느 업무의 서류인지 확정할 수 없으므로 다음처럼 처리합니다.

```
최종 경로: CLARIFY
질문: 어느 업무에 관한 후속 질문인지 선택해 주세요.
```

임의로 최근 업무 하나를 선택하지 않습니다.

### 4-5. 착오송금 기간 질문

착오송금에서 다음 질문은 단순히 이전 업무명만 붙여도 충분하지 않습니다.

```
그럼 얼마나 걸려요?
```

송금인이 묻는 반환지원 처리기간인지, 수취인의 자진반환 기간인지에 따라 검색 대상이 달라질 수 있기 때문입니다.

그래서 현재 결과에서도 다음처럼 처리되었습니다.

```
최종 경로: CLARIFY
판단 사유: MISTAKEN_TRANSFER_TIME_SCOPE_AMBIGUOUS
선택지: 송금인 / 수취인
```

CSV에서도 검색과 답변 생성을 중단하고 약 `0.2ms` 만에 추가질문을 반환했습니다.

### 4-6. 취소·정정·제외

다음 표현은 일반 후속질의보다 먼저 처리됩니다.

```
그만
취소
됐어
착오송금 말고
착오송금이 아니라 채무조정
```

처리 방식은 다음과 같습니다.

| 입력 유형 | 처리 |
| --- | --- |
| 취소 | `DIRECT_RESPONSE`로 종료 |
| A 말고 | A를 제외 상태에 추가 |
| A 말고 B | A 제외, B를 새 활성 업무로 지정 |
| A가 아니라 B | B를 현재 업무로 전환 |
| 제외 업무만 있고 대체 업무 없음 | 어떤 업무를 원하는지 `CLARIFY` |

따라서 과거에 발생했던 “착오송금 말고”를 “착오송금 제외 대상 설명”으로 검색하는 문제를 막는 구조입니다.

### 4-7. 애매한 지시 표현

다음과 같은 경계 표현은 규칙만으로 후속질문 여부를 확정하기 어렵습니다.

```
그 부분은요?
아까 말한 것 말고
신청하는 쪽은요?
처리하는 쪽은요?
```

이때만 HCX-007을 호출하여 다음 구조로 판정합니다.

```
{
  "dialogue_act": "NEW_TOPIC | FOLLOW_UP | CORRECTION | EXCLUSION | AMBIGUOUS",
  "current_question_complete": true,
  "context_required": false,
  "selected_businesses": [],
  "excluded_businesses": [],
  "actor_role": "",
  "missing_slots": [],
  "confidence": 0.0,
  "reason_code": ""
}
```

이 LLM은 답변을 생성하거나 질문을 재작성하지 않습니다. 오직 이전 문맥을 사용할지 판단합니다.

결과가 불확실하면 검색하지 않고 `CLARIFY`합니다.

---

## 5. 최종 라우팅

멀티턴 처리가 끝난 독립질의는 다음 네 경로 중 하나로 분류됩니다.

| 경로 | 의미 | 다음 처리 |
| --- | --- | --- |
| `RETRIEVE` | 검색 가능한 KDIC 질문 | 검색계획 생성 |
| `CLARIFY` | 정답 대상을 확정하기 위한 정보 부족 | 사용자에게 추가질문 |
| `OUT_OF_SCOPE` | KDIC 업무와 명확히 무관 | 범위 안내 후 종료 |
| `DIRECT_RESPONSE` | 인사, 취소, 사용법 등 검색 불필요 | 즉시 응답 |

현재 라우터는 기본적으로 `fail-open retrieval` 정책입니다.

즉, 질문이 명백한 OOS·DIRECT·CLARIFY가 아니라면 검색으로 보냅니다. 애매하다는 이유만으로 검색을 과도하게 막는 것을 방지하기 위한 정책입니다.

---

## 6. 업무 탐지

키워드와 별칭을 기준으로 다음 6개 업무를 탐지합니다.

1. 예금자보호제도
2. 예금보험금 안내
3. 고객 미수령금 신청
4. 착오송금 반환 신청
5. 채무조정 안내
6. 은닉재산 신고

예:

```
보호한도 → 예금자보호제도
미수령금 → 고객 미수령금 신청
잘못 보낸 돈 → 착오송금 반환 신청
신용회복지원 → 채무조정 안내
신고 포상금 → 은닉재산 신고
```

이 단계는 임베딩이나 LLM이 아니라 규칙 기반입니다. 따라서 일반적인 단일질문의 질의분석 시간이 약 `0.5~5ms` 수준으로 짧습니다.

---

## 7. 질의 유형 판정

검색 가능한 질문은 다음 세 가지로 나뉩니다.

### SINGLE

하나의 업무, 하나의 정보요구입니다.

```
채무조정 신청 방법을 알려주세요.
```

처리:

```
원문 또는 문맥이 결합된 독립질의 1개
가중치 1.0
```

### SAME_BUSINESS_MULTI

같은 업무 안에 여러 요구가 포함된 질문입니다.

```
채무조정 신청 자격과 필요서류를 알려주세요.
```

현재 V1.5 정책에서는 분해하지 않고 원문을 유지합니다.

```
검색 질의: 원문 1개
가중치: 1.0
```

같은 업무의 자격과 서류는 동일 문서에 함께 있을 가능성이 높고, 분해하면 문맥 관계가 깨질 수 있기 때문입니다.

### CROSS_BUSINESS

서로 다른 업무가 함께 포함된 질문입니다.

```
미수령금 조회 방법과 착오송금 반환 신청 방법을 알려주세요.
```

이 경우에만 HCX-007 구조화 분해를 호출합니다.

---

## 8. 교차업무 구조화 분해

HCX-007은 답변을 생성하지 않고, 검색용 하위질의를 JSON으로 반환합니다.

개념적으로는 다음과 같습니다.

```
{
  "decomposable": true,
  "subqueries": [
    "고객 미수령금 조회 방법",
    "착오송금 반환지원 신청 방법"
  ],
  "confidence": 0.95,
  "reason": "서로 다른 두 업무의 독립 정보요구"
}
```

모든 복합질문을 호출하는 것이 아니라 다음 조건을 만족할 때만 호출합니다.

```
최종 경로가 RETRIEVE
AND 복합질의 후보
AND 탐지된 업무가 2개 이상
```

단일질의와 동일 업무 복합질의는 HCX-007을 호출하지 않습니다.

---

## 9. 분해 결과 검증

LLM이 하위질의를 반환했다고 바로 사용하지 않습니다. 다음 항목을 검사합니다.

- 하위질의가 최소 2개인지
- 최대 하위질의 수를 초과하지 않았는지
- 예상한 교차업무가 모두 포함됐는지
- 원문에 없는 숫자를 새로 만들지 않았는지
- 원문에 없는 부정·제외 조건을 만들지 않았는지
- 원문의 중요한 부정 조건을 누락하지 않았는지
- 각 하위질의가 원문과 일정 수준 이상의 용어를 공유하는지
- 너무 짧거나 의미 없는 하위질의는 아닌지
- 모델 confidence가 기준 이상인지

검증을 통과하면:

```
분해 승인 = True
```

검증에 실패하면:

```
분해 승인 = False
원문 fallback = True
```

따라서 `분해 승인=False`는 시스템 오류가 아니라, 분해 결과를 검색에 사용하는 것이 안전하지 않다고 판단했다는 뜻일 수 있습니다.

## 10. 검색계획 생성

### 단일질의·동일 업무 복합질의

```
ORIGINAL 1.0
```

### 승인된 교차업무 분해

```
원문 앵커: 0.4
분해질의 전체: 0.6
```

하위질의가 두 개라면:

```
원문                         0.4
업무 A 하위질의              0.3
업무 B 하위질의              0.3
합계                         1.0
```

원문을 0.4 남기는 이유는 분해 과정에서 질문 전체 맥락이나 업무 간 관계가 사라지는 것을 막기 위해서입니다.

### 분해 실패

```
원문 1.0
```

LLM 분해 실패, 검증 거부, API 오류가 발생해도 검색 자체를 중단하지 않습니다.

## 11. 마지막 안전장치

검색으로 넘기기 전에 두 가지를 확인합니다.

### 문맥 업무 보존 검사

이전 업무를 결합한 후속질문이라면, 최종 질의분석 결과에도 그 업무가 남아 있어야 합니다.

예:

```
예상 업무: 채무조정
최종 탐지 업무: 예금보험금
```

처럼 문맥 업무가 사라졌다면 잘못된 검색을 실행하지 않습니다.

```
최종 경로: CLARIFY
사유: CONTEXT_BUSINESS_NOT_PRESERVED
```

### 검색계획 유효성 검사

다음 조건을 확인합니다.

- RETRIEVE인데 검색 질의가 비어 있지 않은지
- 가중치가 유효한지
- 전체 가중치 합이 1.0인지
- 질의 개수가 정상인지
- 잘못된 Hard Filter가 없는지

현재 V1.5 검색계획의 업무 필터는 모두 다음과 같습니다.

```
business_filter.mode = NONE
```

따라서 질의분석 단계에서 특정 업무 문서를 HARD 방식으로 제거하지 않습니다.
