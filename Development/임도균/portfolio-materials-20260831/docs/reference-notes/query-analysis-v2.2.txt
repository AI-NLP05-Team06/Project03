- 2.2 질의분석 테스트 결과
    
    결론부터 말하면, 2.2는 질의분석을 동결하고 검색 단계로 넘어가도 되는 결과입니다.
    
    공식 판정도 다음과 같습니다.
    
    - Hard Gate: 9/9 통과
    - Soft Gate: 8/8 통과
    - 최종 판정: `GO_TO_SEARCH`
    
    ## 1. 가장 중요했던 안전성 문제가 해결됨
    
    모든 Hard Gate를 통과했습니다.
    
    - 270개 전체 질문 평가 완료
    - 캐시 사용 0건
    - 실행 오류 0건
    - 검색 질의 누락 0건
    - 정상 질문을 OOS로 잘못 차단한 경우 0건
    - 정상 질문을 직접 답변으로 잘못 종료한 경우 0건
    - 불필요한 검색 전 추가질문 0건
    - Hard Filter로 정답 업무를 제외한 경우 0건
    - P95 처리시간 약 1.93초
    
    특히 2.1에서 문제가 됐던 다음 질문이 해결됐습니다.
    
    > 파산배당금과 개산지급금 정산금은 무엇이 다른가요?
    > 
    
    2.1에서는 한쪽 업무만 Hard Filter로 고정될 수 있었지만, 2.2에서는 두 업무가 감지되면 `MULTI_BUSINESS_FAIL_OPEN`으로 처리하여 Hard Filter를 사용하지 않습니다.
    
    실제로 복합 업무 질문 9건이 이런 방식으로 안전하게 전체 검색으로 넘어갔고, Hard Filter 정답 제외는 0건입니다.
    
    ## 2. 검색해야 할 질문은 하나도 놓치지 않음
    
    `검색 대상 RETRIEVE Recall`이 100%입니다.
    
    즉, 정답상 검색해야 하는 질문 180개가 모두 검색으로 전달됐습니다. 질의분석이 검색 가능한 질문을 중간에서 잘못 차단한 사례가 없습니다.
    
    업무 분류 Micro F1도 약 91.65%로 기준인 85%를 충분히 넘었습니다.
    
    이는 검색 단계로 넘어갈 때 가장 중요한 결과입니다.
    
    > 검색해야 하는 질문을 질의분석이 막지 않는다.
    > 
    
    ## 3. OOS Fail-Open도 의도대로 작동함
    
    Fail-Open된 질문은 총 28개입니다.
    
    - 실제 KDIC 범위 질문: 8개
    - 실제 범위 밖 질문: 20개
    - 검색 후 범위검사 전달 누락: 0개
    
    예를 들어 다음과 같은 KDIC 관련 질문들이 LLM 판단만 믿었다면 OOS로 잘못 종료될 수 있었습니다.
    
    - 지급명령과 강제집행 절차
    - 부채증명원 발급
    - 개인회생 신청 자격
    - 파산선고와 면책의 관계
    - 신용회복지원
    - 금융부실관련자 정의
    
    2.2는 이 8개 질문을 검색으로 살려냈습니다. 반대로 코스피·비트코인·대출 추천 같은 실제 OOS 질문도 검색으로 넘어가지만, 모두 `post_retrieval_scope_check_required=1`이 붙었습니다.
    
    따라서 검색 단계에서는 반드시 다음 로직을 구현해야 합니다.
    
    ```
    post_retrieval_scope_check_required = 1
            ↓
    검색 결과에 KDIC 관련 근거가 충분한가?
            ↓
    없음 → OUT_OF_SCOPE 또는 INSUFFICIENT_EVIDENCE
    있음 → 정상 답변 진행
    ```
    
    질의분석에서는 안전하게 통과시켰고, 최종 OOS 확정은 검색 결과를 보고 결정하는 구조입니다.
    
    ## 4. 추가질문 탐지는 상당히 개선됨
    
    검색 전 추가질문 Precision은 100%입니다.
    
    즉, 검색 전에 추가질문한 11개는 모두 실제로 추가질문이 필요한 질문이었습니다. 괜한 추가질문은 0건입니다.
    
    검색 후 재검사까지 포함하면 추가질문 필요 질문 60개 중 54개를 잡았습니다.
    
    - 2단계 추가질문 커버리지: 90%
    - 검색 후 검사 후보: 43개
    - 후보 43개 모두 Gold상 추가질문 필요 질문
    - 불필요한 후검사 후보: 0개
    
    2.1의 86.67%보다 개선됐습니다.
    
    아직 탐지되지 않은 질문은 6개입니다.
    
    | ID | 탐지하지 못한 질문 |
    | --- | --- |
    | Q189 | 본인 대신 대리인이 신청할 수 있나요? |
    | Q190 | 상속인이 신청하거나 받을 수 있나요? |
    | Q192 | 신청 과정에서 수수료나 비용이 발생하나요? |
    | Q194 | 이미 접수한 신청을 취소하려면 어떻게 하나요? |
    | Q207 | 미수령금 항목 중 어떤 돈을 신청해야 하나요? |
    | Q232 | 미수령금 신청이 진행되지 않을 때 무엇을 해야 하나요? |
    
    이 6개를 질의분석에서 억지로 모두 잡으려고 규칙을 계속 추가할 필요는 없습니다. 검색된 근거에서 업무와 조건을 확인한 다음 추가질문하면 됩니다.
    
    다만 검색 후 검사 규칙에는 다음 네 가지를 포함하는 것이 좋습니다.
    
    - 업무가 없는 대리인·상속인 질문
    - 업무가 없는 비용·수수료 질문
    - 업무가 없는 신청 취소 질문
    - 조회 결과의 구체적인 항목이나 오류 상태가 필요한 질문
    
    ## 5. 속도도 충분함
    
    - 평균: 약 0.85초
    - 중앙값: 약 0.99초
    - P95: 약 1.93초
    - 270건 전체: 약 3.81분
    - 기존 36분 대비 약 9.45배 빠름
    - LLM 호출률: 약 51.5%
    - 규칙 Fast Path: 약 48.5%
    
    질의분석만 평균 0.85초라면 검색과 답변 생성 시간을 추가하더라도 실제 챗봇에 적용할 수 있는 수준입니다.
    
    2.1보다 평균·P95가 조금 느려졌지만 캐시 없이 전체 270건을 정식 실행한 결과이고, 설정한 기준을 충분히 통과했습니다. 추가 최적화의 우선순위는 낮습니다.
    
    ## 6. 라우팅 정확도 74.44%가 낮아 보이는 이유
    
    일반적인 라우팅 정확도는 74.44%, Macro F1은 53.73%입니다. 숫자만 보면 낮아 보입니다.
    
    하지만 주된 원인은 다음 정책 때문입니다.
    
    ```
    실제 OOS 질문 20개
    → 질의분석에서 OUT_OF_SCOPE로 종료하지 않음
    → 안전하게 RETRIEVE로 전달
    → 일반 라우팅 채점에서는 오답 처리
    ```
    
    따라서 일반 라우팅 정확도는 현재 구조의 운영 성능을 정확히 나타내지 않습니다.
    
    Fail-Open 정책을 반영한 정확도는 81.85%이고, 검색 대상 질문 Recall은 100%, 잘못된 OOS 차단은 0건입니다. 이 세 지표를 더 중요하게 보는 것이 맞습니다.
    
    ## 7. 검색 단계로 넘기기 전에 알아둘 한 가지
    
    `검색 질의 유효율 100%`는 검색어가 비어 있지 않다는 뜻입니다. 복합질문의 모든 정보 요구를 완벽하게 보존했다는 뜻은 아닙니다.
    
    예를 들어 다음 질문입니다.
    
    > 잘못 송금한 돈도 예금자보호 대상인지, 아니라면 착오송금 반환지원은 어떻게 신청하는지 알려주세요.
    > 
    
    생성된 검색 질의는 착오송금 신청 방법 중심이라, 앞부분의 `예금자보호 대상 여부`가 약해졌습니다.
    
    그러므로 검색 단계 평가에서는 단순 Recall@K 외에 다음 지표를 추가하는 것이 좋습니다.
    
    - 복합질의 원자 요청 커버리지
    - 하위 질문별 Gold Chunk 검색 여부
    - 검색 질의 분리 정확도
    - 복합질의 전체 Evidence Coverage

    # **1. V2.2의 목적**
    

V2.2 질의분석의 목적은 사용자의 질문에 직접 제도 답변을 생성하는 것이 아니다.

검색 전에 다음 두 가지를 빠르고 안전하게 결정하는 것이 핵심이다.

1. 이 질문을 검색으로 보내야 하는가?
2. 검색한다면 어떤 질문과 필터 조건으로 검색해야 하는가?

따라서 신청자 유형, 세부 조건, 실제 답변 가능 여부까지 질의분석 단계에서 모두 확정하지 않는다. 검색 근거를 봐야 정확히 판단할 수 있는 사항은 검색 후 검사 필요 상태로 넘긴다.

V2.2의 설계 방향은 다음과 같다.

- 단순하고 명확한 질문은 규칙으로 빠르게 처리한다.
- 규칙만으로 판단하기 어려운 질문에만 HCX를 호출한다.
- LLM이 범위 밖으로 판단했더라도 애매하면 검색으로 보낸다.
- 개인 조건이 부족해도 업무가 확인되면 먼저 검색한다.
- 여러 업무가 함께 등장하면 한 업무로 강제 필터링하지 않는다.
- 검색 전 판단과 검색 후 판단을 분리한다.

# **3. 실제 실행 순서와 중심 함수**

V2.2의 중심 함수는 다음 함수다.

run_minimal_query_pipeline(question, conversation_context=None)

이 함수 안에서 다음 순서로 처리가 진행된다.

질문 입력

→ 정규화

→ 후속 문맥 복원

→ 직접응답·명백한 OOS 규칙

→ 검색 전 추가질문 규칙

→ Fast Retrieve 규칙

→ 필요한 경우에만 HCX 호출

→ OOS Fail-Open

→ 검색 후 검사 필요 여부 표시

→ 검색 필터 정책 결정

→ 최종 질의분석 JSON 반환

실제 코드의 핵심 구조는 다음과 같다.

selected = rule_direct_or_oos(contextualized)

if selected is None:

selected = rule_clarify(contextualized)

if selected is None:

selected = fast_retrieve(contextualized)

if selected is not None:

result, decision_source = selected

else:

analysis_input = build_analysis_input(

contextualized,

conversation_context,

)

result, llm_meta = call_hcx_minimal(analysis_input)

decision_source = "LLM_MINIMAL"

규칙에서 결과가 나오면 HCX를 호출하지 않는다. 세 규칙에서 모두 판단하지 못한 질문만 HCX로 보낸다.

# **4. 1단계: 사용자 질문 입력**

사용자가 입력한 원문은 original_query에 보존한다.

original = clean_text(question)

빈 질문이면 실행을 중단한다.

if not original:

raise ValueError("질문이 비어 있습니다.")

원문을 보존하는 이유는 다음과 같다.

- 질의 보정 전후를 비교할 수 있다.
- 검색 질의가 원래 의미를 바꿨는지 확인할 수 있다.
- 운영 로그와 오류 분석에 활용할 수 있다.
- 검색 결과가 좋지 않을 경우 원문 검색으로 되돌릴 수 있다.
- LLM이 검색 질의를 잘못 줄였을 때 누락된 요구를 찾을 수 있다.

주요 입력·중간 필드는 다음과 같다.

| **필드** | **의미** |
| --- | --- |
| original_query | 사용자가 입력한 원문 |
| normalized_query | 최소 정규화가 적용된 질문 |
| contextualized_query | 이전 대화 문맥이 복원된 질문 |

# **5. 2단계: 최소 정규화**

사용 함수는 다음과 같다.

minimal_normalize()

수행하는 작업은 다음과 같다.

- 불필요한 연속 공백을 하나로 정리한다.
- 반복된 감정 표현 일부를 정리한다.
- 명백한 오탈자를 수정한다.
- 붙어 있는 일부 단어를 분리한다.
- 질문의 업무명과 의미는 임의로 바꾸지 않는다.

예시:

입력: 신청서류가 머에요???

출력: 신청 서류가 뭐예요??

현재 적용된 치환 예시는 다음과 같다.

| **입력** | **보정** |
| --- | --- |
| 머에요 | 뭐예요 |
| 뭐에요 | 뭐예요 |
| 되여 | 돼요 |
| 됬 | 됐 |
| 신청서류 | 신청 서류 |

실제 코드는 다음과 같은 구조다.

def minimal_normalize(question: str) -> str:

text = clean_text(question)

text = re.sub(

r"([!?~ㅋㅎㅠㅜ])\1{2,}",

r"\1\1",

text,

)

replacements = {

"머에요": "뭐예요",

"뭐에요": "뭐예요",

"되여": "돼요",

"됬": "됐",

"신청서류": "신청 서류",

}

정규화 결과는 normalized_query에 저장한다.

# **6. 3단계: 후속 질문 문맥 복원**

## **현재 구현의 한계**

현재는 최근 대화 중 업무 표현이 있는 이전 사용자 질문 하나를 중심으로 복원한다.

따라서 다음과 같은 복잡한 대화는 완벽하게 처리하지 못할 수 있다.

- 여러 업무가 대화에서 동시에 진행된 경우
- 업무명이 없고 대상만 이어지는 경우
- 이전 답변에서 새롭게 등장한 조건을 참조하는 경우
- “두 번째 경우는요?”처럼 답변 구조를 참조하는 질문
- 여러 턴 전에 말한 금액·상품·역할을 다시 참조하는 질문

V2.2에서는 속도를 위해 짧은 문맥 복원만 수행한다. 장기 대화가 필요하면 별도의 대화 상태 저장소가 필요하다.

# **7. 4단계: 규칙 기반 빠른 처리**

V2.2는 모든 질문을 HCX에 보내지 않는다.

먼저 세 가지 규칙을 순서대로 검사한다.

1. 직접 응답 또는 명백한 OOS

2. 업무가 없는 일반 질문

3. 명확한 검색 질문

실제 실행 순서는 다음과 같다.

selected = rule_direct_or_oos(contextualized)

if selected is None:

selected = rule_clarify(contextualized)

if selected is None:

selected = fast_retrieve(contextualized)

세 규칙 중 하나에서 결과가 나오면 HCX를 호출하지 않는다.

이 경로를 Fast Path라고 볼 수 있다. V2.2 평가에서는 전체 질문의 약 48.5%가 LLM 호출 없이 처리됐다.

# **12. 5단계: HCX 최소 질의분석**

규칙으로 처리하지 못한 질문만 HCX-005에 전달한다.

사용 함수는 다음과 같다.

call_hcx_minimal()

HCX가 생성하는 필드는 정확히 다섯 개다.

{

"route_type": "",

"business_functions": [],

"search_queries": [],

"clarification_reason": "",

"clarification_question": ""

}

## **필드 정의**

| **필드** | **의미** |
| --- | --- |
| route_type | RETRIEVE, CLARIFY, OUT_OF_SCOPE 중 하나 |
| business_functions | 관련된 KDIC 업무 목록 |
| search_queries | 검색 시스템에 전달할 검색 질문 |
| clarification_reason | 추가질문이 필요한 이유 |
| clarification_question | 사용자에게 물어볼 추가질문 |

## **왜 5개만 생성하는가?**

기존 질의분석에서는 다음과 같은 많은 필드를 한 번에 생성하려고 했다.

- 사용자 역할
- 신청자 유형
- 원자 요청
- 요청 관계
- Missing Slot
- 복잡도
- 세부 의도
- 조건
- 추가질문
- 검색 질의

이렇게 하면 다음 문제가 발생한다.

- 출력 토큰이 증가한다.
- 응답 시간이 증가한다.
- JSON 형식 오류가 증가한다.
- 필드 간 판단이 서로 모순될 수 있다.
- 검색 전에는 알 수 없는 정보까지 억지로 판단한다.
- 한 질문을 분석하는 데 여러 차례 LLM 호출이 필요해질 수 있다.

V2.2는 검색 전에 반드시 필요한 정보만 HCX에 요구한다.

# **13. HCX 프롬프트의 핵심 규칙**

프롬프트에서 HCX의 역할은 답변 생성기가 아니라 검색 전 최소 질의 라우터로 정의된다.

핵심 규칙은 다음과 같다.

1. 사용자 질문에 제도 내용을 답변하지 않는다.

2. 검색 경로만 JSON으로 결정한다.

3. 업무가 하나라도 확인되면 OOS로 판단하지 않는다.

4. 업무는 확인되지만 개인 조건이 부족하면 우선 검색한다.

5. 업무 없이 신청 방법·서류·기한만 물으면 추가질문한다.

6. RETRIEVE이면 독립적으로 검색 가능한 질문을 만든다.

7. 복합질문만 여러 검색 질의로 분리한다.

8. 금액·날짜·부정·대상 조건을 보존한다.

9. 질문에 없는 사실을 추가하지 않는다.

10. 지정된 5개 필드 외에는 출력하지 않는다.

프롬프트 예시는 다음과 같다.

질문: 예금보험금은 어떤 경우에 지급되나요?

출력:

{

"route_type": "RETRIEVE",

"business_functions": ["예금보험금 안내"],

"search_queries": ["예금보험금 지급 조건은 무엇인가요?"],

"clarification_reason": "",

"clarification_question": ""

}

업무가 없는 질문 예시는 다음과 같다.

질문: 신청 서류가 무엇인가요?

출력:

{

"route_type": "CLARIFY",

"business_functions": [],

"search_queries": [],

"clarification_reason": "BUSINESS_NOT_SPECIFIED",

"clarification_question": "어떤 제도나 업무의 신청 서류를 확인하고 싶으신가요?"

}

# **14. JSON 출력 검증**

사용 함수는 다음과 같다.

validate_minimal_payload()

HCX 출력은 그대로 사용하지 않고 코드로 검증한다.

검증 사항은 다음과 같다.

- route_type이 허용된 값인가?
- 업무명이 6개 허용 업무 중 하나인가?
- 검색 질의가 배열인가?
- RETRIEVE인데 검색 질의가 비어 있지 않은가?
- RETRIEVE가 아닌데 검색 질의가 들어 있지는 않은가?
- 허용하지 않은 추가 필드가 들어왔는가?

허용 라우팅 값은 다음과 같다.

RETRIEVE

CLARIFY

OUT_OF_SCOPE

예를 들어 HCX가 다음처럼 반환하면 오류 처리한다.

{

}

"route_type": "RETRIEVE",

"search_queries": []

오류:

RETRIEVE_WITHOUT_SEARCH_QUERY

RETRIEVE가 아니면 코드가 search_queries를 빈 배열로 정리한다. LLM이 실수로 CLARIFY 결과에 검색 질의를 넣더라도 검색이 실행되지 않게 한다.

# **15. JSON 형식 복구**

사용 함수는 다음과 같다.

extract_json_object()

repair_json_text()

HCX가 JSON 앞뒤에 설명을 붙이거나 코드블록을 넣어도 JSON 객체 부분을 추출한다.

처리 대상 예시는 다음과 같다.

다음은 분석 결과입니다.

{ "route_type": "RETRIEVE" }

또한 문자열 배열에서 쉼표가 일부 누락된 경우 간단한 복구를 시도한다.

그래도 JSON이 아니면 HCX에 한 번만 재요청한다.

직전 출력은 질의분석 JSON이 아니라서 폐기합니다.

정책 설명과 사용자 답변을 작성하지 마세요.

반드시 지정된 다섯 키만 가진 JSON 객체 하나를 출력하세요.

첫 문자는 중괄호 열기, 마지막 문자는 중괄호 닫기여야 합니다.

JSON 복구 재호출은 최대 1회다.

무한 재요청하지 않는 이유는 다음과 같다.

- 지연시간이 계속 증가하는 것을 방지한다.
- 동일한 형식 오류가 반복되는 것을 방지한다.
- 운영 중 실패 원인을 로그에서 명확히 확인한다.

# **16. API 요청 안정화**

429 Rate Limit과 JSON 오류는 서로 다른 문제로 처리한다.

## **16.1 429 오류**

사용 함수는 다음과 같다.

rate_limit_wait_seconds()

응답 헤더의 다음 값을 확인한다.

- retry-after
- x-ratelimit-reset-requests
- x-ratelimit-reset-tokens

헤더가 없으면 점진적으로 대기시간을 늘린다.

1차 재시도: 약 20초

2차 재시도: 약 40초

3차 재시도: 약 60초

약간의 랜덤 지연도 추가해 동시 재요청 충돌을 줄인다.

## **16.2 호출 간 최소 간격**

MIN_CALL_INTERVAL_SECONDS = 0.5

연속 API 호출 사이에 최소 0.5초 간격을 둔다.

## **16.3 재시도 분리 이유**

429 오류

→ 기다린 후 동일 요청

JSON 오류

→ 형식 교정 프롬프트로 재요청

429 오류를 JSON 문제처럼 처리하거나 JSON 오류를 단순 재시도하면 같은 실패가 반복될 수 있다.

# **17. 6단계: OOS Fail-Open**

사용 함수는 다음과 같다.

apply_oos_fail_open()

V2.2의 가장 중요한 안전장치 중 하나다.

LLM이 OUT_OF_SCOPE로 판단했더라도 바로 종료하지 않는다.

LLM OUT_OF_SCOPE

↓

RETRIEVE로 변경

↓

원문을 검색 질의로 사용

↓

검색 후 범위검사 필요 표시

변경되는 필드는 다음과 같다.

{

"route_type": "RETRIEVE",

"search_queries": [

"사용자의 원래 질문"

],

"oos_fail_open_applied": 1,

"post_retrieval_scope_check_required": 1,

"post_retrieval_scope_check_reason": "OOS_FAIL_OPEN"

}

## **왜 필요한가?**

LLM이 다음과 같은 KDIC 관련 질문을 OOS로 오판할 수 있기 때문이다.

파산선고를 받으면 바로 면책되나요?

부채증명원은 어떻게 발급받나요?

금융부실관련자는 누구인가요?

지급명령 이후 강제집행 절차는 어떻게 되나요?

LLM 판단만 믿고 종료하면 검색 자체가 실행되지 않는다.

Fail-Open은 잘못된 종료보다 한 번 더 검색하는 쪽을 선택한 정책이다.

## **예외**

코드의 명백한 OOS 정규식으로 탐지된 질문은 Fail-Open하지 않는다.

오늘 날씨

맛집 추천

주식 종목 추천

이 질문들은 FAST_RULE_OUT_OF_SCOPE에서 종료된다.

# **18. 7단계: 검색 후 추가질문 후보 탐지**

사용 함수는 다음과 같다.

detect_post_retrieval_check()

이 함수는 지금 사용자에게 추가질문하는 함수가 아니다.

검색 결과를 본 다음 추가질문 여부를 다시 검사해야 한다는 표시만 만든다.

반환 예:

{

"post_retrieval_check_required": 1,

"post_retrieval_check_reasons": [

"TARGET_OR_PRODUCT"

]

}

## **탐지 유형**

| **코드** | **의미** | **질문 예시** |
| --- | --- | --- |
| APPLICANT_TYPE | 신청자 유형 확인 필요 | 제 신청 유형에 맞는 서류는? |
| TARGET_OR_PRODUCT | 대상 상품·금액·거래 확인 필요 | 이 상품도 보호되나요? |
| PERSONAL_CASE | 개인 상황 판단 필요 | 제 상황을 기준으로 판단해 주세요 |
| AMOUNT_OR_CALCULATION | 개인 금액 계산 필요 | 제 경우 얼마까지 보호되나요? |
| REJECTION_OR_SUPPLEMENT | 거절·보완·처리 지연 확인 필요 | 신청이 반려됐는데 무엇을 보완하나요? |

## **역할 정보 처리**

코드는 역할이 이미 명시됐는지와 역할이 빠졌는지를 구분한다.

명시된 역할 예:

대리인이 신청할 때 필요한 서류

상속인으로 신청할 때 필요한 서류

법인이 신청할 때 필요한 서류

빠진 역할 예:

제 신청 유형에 맞는 서류

제 경우 누가 방문해야 하나요?

신청인란에 누구를 적어야 하나요?

역할이 이미 분명하면 역할을 다시 묻지 않는다. 역할이 실제로 필요한데 질문에 없을 때만 APPLICANT_TYPE 후보로 표시한다.

## **처리 방식**

질문에서 조건 부족 가능성 발견

↓

우선 검색 실행

↓

검색 결과에 조건 분기가 있는지 확인

↓

현재 정보로 답변 가능하면 답변

↓

개인 조건이 필요하면 추가질문

예시:

이 상품도 예금자보호 대상인가요?

검색 전에는 상품 정보가 부족하지만, 먼저 예금자보호 대상 상품 기준을 검색할 수 있다.

검색 결과에 상품 유형별 조건이 있다면 다음처럼 추가질문한다.

어떤 금융회사에서 가입한 어떤 상품인지 알려주시겠어요?

# **19. 8단계: 질문 유형 파생**

사용 함수는 다음과 같다.

derive_question_type()

별도 LLM 호출 없이 검색 질의 개수로 파생한다.

검색 질의 1개

→ SINGLE_RETRIEVE

검색 질의 2개 이상

→ MULTI_RETRIEVE

검색이 아닌 경우

→ CLARIFY, OUT_OF_SCOPE, DIRECT_RESPONSE

출력 필드 예:

{

"question_type_derived": "SINGLE_RETRIEVE"

}

이 필드는 검색 실행 방식을 구분하거나 운영 로그를 분석할 때 사용한다.

주의할 점은 검색 질의가 하나라고 해서 사용자 정보 요구가 반드시 하나인 것은 아니라는 것이다. HCX가 복합질의를 하나의 검색 질의로 합쳤을 수 있으므로 검색 단계에서 원자 요청 커버리지를 별도로 평가해야 한다.

# **20. 9단계: 검색 필터 정책 결정**

사용 함수는 다음과 같다.

build_search_policy()

검색할 때 업무 필터를 얼마나 강하게 적용할지 결정한다.

검색 정책은 세 가지다.

HARD

SOFT

NONE

## **20.1 HARD Filter**

다음 조건을 모두 만족해야 한다.

1. 질문에 명시적인 업무 표현이 정확히 하나 있다.
2. 분석된 업무도 정확히 하나다.
3. 명시적 업무와 분석 결과가 같다.

예시:

착오송금 반환지원 신청 기한은 언제인가요?

결과:

{

"business_filter_mode": "HARD",

"business_filters": [

"착오송금 반환 신청"

],

"explicit_businesses": [

"착오송금 반환 신청"

],

"filter_evidence": "SINGLE_EXPLICIT_QUERY_TERM"

}

검색 시스템에서는 착오송금 업무 청크로 범위를 제한할 수 있다.

## **20.2 SOFT Filter**

업무 가능성은 있지만 확정할 수 없을 때 사용한다.

예시:

빚을 줄일 수 있는 지원이 있나요?

채무조정 업무일 가능성은 높지만 질문에 명시적인 업무명이 없다.

결과:

{

"business_filter_mode": "SOFT",

"business_filters": [

"채무조정 안내"

],

"explicit_businesses": [],

"filter_evidence": "MODEL_OR_NON_UNIQUE_EVIDENCE"

}

검색에서는 해당 업무 청크의 점수를 높이되 다른 업무 청크를 제거하지 않는다.

## **20.3 NONE**

업무가 불확실하거나 여러 업무가 동시에 감지되면 필터를 적용하지 않는다.

예시:

파산배당금과 개산지급금 정산금은 무엇이 다른가요?

감지 업무:

예금보험금 안내

고객 미수령금 신청

결과:

{

"business_filter_mode": "NONE",

"business_filters": [],

"explicit_businesses": [

"예금보험금 안내",

"고객 미수령금 신청"

],

"filter_evidence": "MULTI_BUSINESS_FAIL_OPEN"

}

한 업무만 Hard Filter로 적용하면 다른 업무의 청크를 잃을 수 있기 때문에 전체 검색한다.

## **route_type 처리**

DIRECT_RESPONSE

필요 정보 충분

# **23. 배치 평가 코드**

평가 실행 함수는 다음과 같다.

run_batch()

V2.2의 기본 설정은 다음과 같다.

RUN_FULL_DATASET = True

FORCE_RERUN = True

의미는 다음과 같다.

- 평가데이터 270개 전체를 실행한다.
- 기존 캐시를 사용하지 않는다.
- 실제 API 호출 결과로 평가한다.
- 평가 결과를 캐시에 새로 저장한다.

캐시 키는 다음 값으로 구성된다.

파이프라인 버전

+ HCX 모델

+ 평가 ID

+ 질문

cache_key = (

f"{PIPELINE_VERSION}|{HCX_MODEL}|"

f"{evaluation_id}|{question}"

)

질문, 모델 또는 파이프라인 버전이 바뀌면 다른 캐시로 인식한다.

## **오류 처리**

각 질문은 독립적으로 실행한다. 한 질문에서 오류가 발생해도 전체 평가를 즉시 중단하지 않고 error_result()를 저장한다.

오류 결과에는 다음 정보가 기록된다.

- error_type
- error_message
- status=ERROR
- 처리 중 생성된 기본 필드
- 캐시 사용 여부

decision_source 예시는 다음과 같다.

| **값** | **의미** |
| --- | --- |

# **25. 평가 구조**

V2.2는 Hard Gate와 Soft Gate를 분리한다.

## **25.1 Hard Gate**

반드시 모두 통과해야 한다.

| **Gate** | **기준** | **의미** |
| --- | --- | --- |
| 전체 평가 실행 | 270/270 | 일부 문항만 평가한 결과로 통과시키지 않음 |
| 캐시 미사용 | 0건 | 정식 평가에서 이전 결과 재사용 금지 |
| 실행 성공률 | 99.5% 이상 | 운영 안정성 |
| 검색 질의 유효율 | 99% 이상 | RETRIEVE 결과에 검색 질의 존재 |
| 정상 질문 False OOS | 0건 | 검색할 질문을 범위 밖으로 차단하지 않음 |
| 정상 질문 False DIRECT | 0건 | 검색할 질문을 직접응답으로 종료하지 않음 |
| 과잉 검색 전 CLARIFY | 0건 | 검색 가능한 질문을 불필요하게 막지 않음 |
| Hard Filter Gold 제외 | 0건 | 정답 업무 청크를 필터로 제거하지 않음 |
| P95 처리시간 | 2.5초 이하 | 사용자 대기시간 관리 |

## **25.2 Soft Gate**

8개 중 6개 이상 통과해야 한다.

| **Gate** | **기준** | **의미** |
| --- | --- | --- |
| Fail-Open 보정 라우팅 정확도 | 80% 이상 | 운영 정책을 반영한 라우팅 정확도 |
| 검색 대상 RETRIEVE Recall | 98% 이상 | 검색해야 할 질문을 검색으로 보낸 비율 |
| 업무 분류 Micro F1 | 85% 이상 | 업무 분류 성능 |
| 검색 전 추가질문 Precision | 95% 이상 | 불필요한 추가질문 억제 |
| 검색 전·후 추가질문 커버리지 | 85% 이상 | 2단계 추가질문 탐지 성능 |
| LLM 호출률 | 60% 이하 | 경량화 수준 |
| 평균 질의분석 시간 | 1.5초 이하 | 평균 응답 지연 관리 |
| Fail-Open 범위검사 전달률 | 100% | 검색 후 OOS 재검사 누락 방지 |

최종 판정은 다음과 같다.

Hard Gate 전부 통과

+

GO_TO_SEARCH

# **26. 질문 유형별 실제 처리 예시**

## **예시 A: 명확한 단순 질문**

예금보험금 신청 기한은 언제인가요?

처리:

최소 정규화

→ 업무 1개 탐지

→ 기간 속성 탐지

→ Fast Retrieve

→ HARD Filter

→ 검색

HCX 호출 없음.

## **예시 B: 업무가 없는 질문**

신청 서류가 무엇인가요?

처리:

업무 탐지 실패

→ 일반 신청 서류 패턴 탐지

→ CLARIFY

추가질문:

어떤 제도나 업무의 신청 서류를 확인하고 싶으신가요?

## **예시 C: 개인 조건이 필요한 질문**

이 상품도 예금자보호 대상인가요?

처리:

예금자보호 업무 확인

→ 우선 RETRIEVE

→ TARGET_OR_PRODUCT 표시

→ 검색 실행

→ 근거의 조건 분기 확인

→ 상품 정보가 필요하면 추가질문

검색 전에 무조건 막지 않는다.

## **예시 D: LLM이 OOS로 판단한 KDIC 질문**

파산선고를 받으면 바로 면책되나요?

처리:

규칙 처리 실패

→ HCX 호출

→ HCX가 OOS 판단

→ OOS Fail-Open

→ RETRIEVE로 변경

→ 검색 후 범위검사 표시

→ 검색 실행

검색 결과에 KDIC 근거가 있으면 정상 답변한다.

## **예시 E: 복수 업무 질문**

파산배당금과 개산지급금 정산금은 무엇이 다른가요?

처리:

예금보험금 업무 감지

+

고객 미수령금 업무 감지

→ MULTI_BUSINESS_FAIL_OPEN

→ 업무 Hard Filter 미적용

→ 전체 검색

한 업무의 청크가 필터로 제거되는 것을 방지한다.

## **예시 F: 명백한 범위 밖 질문**

오늘 날씨가 어때요?

처리:

FAST_RULE_OUT_OF_SCOPE

→ 검색하지 않음

→ 지원 범위 안내

## **예시 G: 후속 질문**

이전 질문: 착오송금 반환지원은 어떻게 신청하나요?

현재 질문: 그럼 기한은요?

처리:

후속 표현 탐지

→ 이전 업무 질문 결합

→ 착오송금 반환지원 신청 기한 검색

# **27. V2.2의 장점**

## **27.1 속도**

전체 질문의 약 절반은 LLM을 호출하지 않는다.

Fast Path 약 48.5%

LLM 호출률 약 51.5%

평균 약 0.85초

P95 약 1.93초

## **27.2 안전성**

- 정상 질문을 OOS로 잘못 차단하지 않는다.
- 여러 업무가 있는 질문에 Hard Filter를 적용하지 않는다.
- 개인 조건이 부족해도 검색 자체는 먼저 수행한다.
- 검색 후 검사 사유를 구조화해 전달한다.
- LLM 출력 JSON을 코드로 검증한다.
- 검색해야 할 질문을 직접응답으로 잘못 종료하지 않는다.

## **27.3 구조적 단순성**

HCX 출력 필드를 5개로 제한했다.

따라서 복잡한 질의분석 모델보다 구현·운영·평가가 단순하다.

## **27.4 판단 책임 분리**

검색 전 질의분석

→ 검색 가능 여부와 검색 계획

검색 후 검사

→ 근거 충분성, 추가질문, 범위 확정

답변 단계

→ 근거에 충실한 최종 답변 생성

각 단계가 자신에게 필요한 판단만 수행하므로 질의분석이 과도하게 무거워지지 않는다.

# **28. V2.2의 한계**

## **28.1 키워드 사전 의존**

새로운 표현이 사전에 없으면 Fast Path에서 처리하지 못한다.

다만 이 경우 대부분 HCX로 넘어가므로 검색이 완전히 차단되지는 않는다.

## **28.2 복합질의 분리가 완벽하지 않음**

예시:

잘못 송금한 돈도 예금자보호 대상인지,

아니라면 반환지원은 어떻게 신청하는지 알려주세요.

HCX가 착오송금 검색 질의만 만들면 예금자보호 요구가 누락될 수 있다.

따라서 검색 평가에서 원자 요청별 검색 커버리지를 별도로 확인해야 한다.

## **28.3 검색 질의 유효율의 의미가 제한적**

검색 질의 유효율 100%는 RETRIEVE 결과에 검색어가 비어 있지 않다는 뜻이다.

복합질문의 모든 정보 요구가 보존됐다는 뜻은 아니다.

## **28.4 검색 후 검사는 표시만 생성**

V2.2는 다음 필드를 생성할 뿐 실제 추가질문을 확정하지 않는다.

{

"post_retrieval_check_required": 1

}

검색 시스템 또는 Evidence 검사기가 이 필드를 실제로 사용해야 한다.

## **28.5 OOS 확정이 검색 단계로 이동**

Fail-Open된 실제 OOS 질문도 검색을 한 번 수행한다.

안전성은 높지만 소량의 검색 비용이 추가된다.

## **28.6 후속 문맥 복원이 단순함**

현재는 이전 사용자 질문 하나를 중심으로 복원한다. 복잡한 장기 대화 상태는 별도의 대화 상태 저장소가 필요하다.

## **28.7 규칙 사전 유지보수 필요**

업무 용어와 제도명이 변경되면 다음 사전을 갱신해야 한다.

- BUSINESS_TERMS
- HARD_FILTER_TERMS
- KDIC_SCOPE_ANCHORS
- SEARCH_ASPECT_TERMS
- 추가질문 탐지 정규식

# **29. V2.2 이후 검색 단계의 필수 구현**

V2.2를 검색 시스템에 연결할 때 다음 기능이 필요하다.

1. search_queries별 Hybrid 검색

2. HARD·SOFT·NONE 필터 정책 적용

3. 복수 검색 질의 결과 통합

4. 검색 후 KDIC 범위 검사

5. 검색 후 추가질문 필요 여부 검사

6. Evidence Pack 구성

7. 검색 결과가 없을 때 제한 답변

특히 다음 두 필드는 선언만 하고 무시하면 안 된다.

post_retrieval_scope_check_required

post_retrieval_check_required

검색 단계가 이 필드를 사용하지 않으면 V2.2의 OOS Fail-Open과 2단계 추가질문 구조가 완성되지 않는다.

## **검색 단계 권장 평가 지표**

| **지표** | **확인 목적** |
| --- | --- |
| Recall@20 | 후보군 안에 Gold 청크가 포함되는지 |
| Recall@5 | 답변에 전달할 상위 결과의 정확성 |
| Gold Chunk 미검색률 | 필요한 근거를 완전히 놓친 비율 |
| Hard Filter Gold 제외율 | 필터 때문에 정답 근거가 제거됐는지 |
| 복합질의 원자 요청 커버리지 | 하위 정보 요구를 모두 검색했는지 |
| 빈 검색 결과율 | 검색 결과가 전혀 없는 질문 비율 |
| 검색 후 OOS 정확도 | Fail-Open 질문을 최종적으로 올바르게 판정했는지 |
| 검색 후 추가질문 정확도 | 실제 필요한 경우에만 추가질문했는지 |

# **30. 최종 요약**

V2.2는 다음과 같은 혼합형 질의분석 구조다.

간단하고 명확한 질문

→ 규칙으로 빠르게 처리

규칙으로 판단하기 어려운 질문

→ HCX 최소 5필드 분석

LLM이 OOS로 판단한 애매한 질문

→ 안전하게 검색으로 전달

개인 조건이 부족한 질문

→ 먼저 검색하고 이후 추가질문 판단

업무가 여러 개인 질문

→ Hard Filter 없이 전체 검색

핵심 설계 원칙은 다음 한 문장으로 정리할 수 있다.

> 질의분석에서 모든 것을 확정하려 하지 않고, 검색에 필요한 최소 정보만 빠르게 만들며, 확실하지 않은 질문은 차단하지 않고 검색 결과를 보고 최종 판단한다.
> 

V2.2 평가에서는 Hard Gate 9개와 Soft Gate 8개를 모두 통과했다. 따라서 질의분석을 계속 무겁게 확장하기보다 이 버전을 동결하고 검색 시스템 연결과 검색 성능평가로 넘어가는 것이 적절하다.
