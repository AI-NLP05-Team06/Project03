## 하드 게이트

## 결론

질의 재작성 O가 복합질의 검색에는 확실히 도움을 줬습니다. 하지만 현재처럼 “원문을 버리고 재작성 질의만 검색”하는 방식은 최종안으로 쓰기 어렵습니다.

가장 좋은 다음 방향은:

> 원문 검색 + 분리된 재작성 질의 검색을 함께 실행하고 결과를 융합하는 방식
> 

입니다.

## 1. 전체 결과

89문항, O/X 각각 89건으로 총 178개 결과입니다.

| 지표 | 재작성 O | 재작성 X | 차이 |
| --- | --- | --- | --- |
| 라우팅 통과율 | 87.64% | 87.64% | 동일 |
| Hit@3 | 85.71% | 79.22% | O +6.49%p |
| Recall@5 | 71.80% | 65.69% | O +6.10%p |
| E2E Hit@3 | 75.00% | 69.32% | O +5.68%p |
| E2E Recall@5 | 62.82% | 57.48% | O +5.34%p |
| Primary Recall@5 | 70.78% | 68.83% | O +1.95%p |
| Supporting Recall@5 | 63.53% | 56.49% | O +7.03%p |
| 전체 근거 회수율 | 49.35% | 45.45% | O +3.90%p |

특히 Supporting Recall이 7.03%p 상승했습니다.

복합질문은 첫 번째 핵심 청크만 찾는 것보다 두 번째·세 번째 근거까지 함께 찾는 것이 중요하므로, 재작성의 효과가 가장 잘 나타난 부분입니다.

## 2. 문항별 승패

O와 X가 모두 정상 검색된 76문항을 직접 비교하면:

- 재작성 O 승리: 18문항
- 원문 X 승리: 5문항
- 동일: 53문항
- 전체 근거 회수 기준:
    - O 승리 9문항
    - X 승리 5문항

즉 재작성은 대체로 이득이지만, 약 70%의 질문에서는 결과가 동일했습니다. 모든 복합질문에 무조건 재작성을 적용하면 불필요한 레이턴시가 발생할 수 있습니다.

## 3. 재작성이 크게 도움 된 질문

대표적으로 Q090입니다.

> 예전에 못 받은 미수령금을 찾는 방법과 최근 잘못 송금한 돈의 반환지원 신청 방법을 각각 알려주세요.
> 

재작성 O:

- 고객 미수령금 신청 방법
- 착오송금 반환지원 신청 방법

결과:

- O Recall@5: 100%
- X Recall@5: 0%

서로 다른 두 업무가 한 문장에 들어 있으면 원문 검색에서는 한쪽 업무가 검색 결과를 장악할 수 있습니다. 재작성은 이를 두 개로 분리하여 양쪽 근거를 모두 찾았습니다.

다음 유형에서도 효과가 컸습니다.

- 예금자보호 한도 + 예금보험금 신청
- 미수령금 + 착오송금
- 예금자보호 + 착오송금 금액 기준
- 개인회생 + 개인파산 비교
- 반환지원 기간 + 비용 차감 방식

## 4. 재작성이 오히려 손해를 낸 질문

대표적으로 Q112입니다.

> 송금인 본인이 신청할 때 필요한 서류와 접수 방법은 무엇인가요?
> 

결과:

- O Recall@5: 0%
- X Recall@5: 100%

재작성 문장 자체는 자연스러웠지만, 검색 결과가 시행세칙·규정 청크 쪽으로 치우치면서 실제 안내 청크가 Top-5에서 빠졌습니다.

손해 사례는 총 5문항입니다.

- 송금인 본인 신청 서류와 접수 방법
- 지급명령과 강제집행
- 간편송금과 해외계좌 제외
- 은행·저축은행의 보호상품
- 반환지원 신청 전 조치와 접수 후 절차

이 사례들의 공통점은 원문에 이미 검색에 유리한 구체적인 표현이 있었는데, 재작성하면서 그 표현이 일반화됐다는 점입니다.

예:

```
은행과 저축은행
→ 어떤 금융회사
```

이렇게 바뀌면 `저축은행`이라는 중요한 검색 신호가 사라집니다.

## 6. 라우팅 문제가 검색 성능을 막고 있음

89개 모두 Gold가 `MULTI_RETRIEVE`인데 공통 라우터는 11개를 `CLARIFY`로 판단했습니다.

그 결과 해당 문항들은 O/X 모두 검색 결과가 0개입니다.

대표적인 오분류:

- 고객 미수령금과 착오송금 반환지원
- 예금보험금 지급 조건과 은닉재산
- 예금자보호 한도와 미수령금
- 미수령금과 채무조정
- 예금보험금과 금융부실관련자

특히 서로 다른 업무가 섞인 그룹은 20문항 중 5문항이 CLARIFY가 되어 라우팅 통과율이 75%에 불과합니다.

이 질문들은 업무가 불분명한 게 아니라 여러 업무가 동시에 명시된 것입니다.

따라서 규칙을 다음처럼 고치는 것이 좋습니다.

```
서로 다른 KDIC 업무가 2개 이상 명시됨
→ CLARIFY 금지
→ MULTI_RETRIEVE
```

현재 검색 성능보다 라우팅 단계에서 발생하는 12.36%의 손실을 먼저 줄일 필요가 있습니다.

## 8. 오류 및 답변 품질 문제

오류는 두 건입니다.

- Q080 재작성 O
    - HCX가 JSON 객체가 아닌 JSON 배열을 반환
    - 재작성 질의가 비어 오류
- Q180 재작성 X
    - Answer Skeleton JSON의 잘못된 escape 문자
    - Skeleton 파싱 실패

수정 방향:

- 재작성 결과가 `[{search_query: ...}]` 형태여도 허용
- Skeleton JSON 파싱 실패 시 자동 복구 1회
- 답변 실패와 검색 실패를 서로 다른 상태로 기록

답변 품질도 검색지표만으로 보장되지는 않습니다.

발견된 문제:

- 검색에 성공한 답변 중 11개는 인식 가능한 청크 인용이 없었음
- `[C1]`, `(C1)`, `[^C1]` 형식이 혼재
- 7개 답변에서 프롬프트가 금지한 전화번호가 출력됨
- Q090 O는 검색 근거는 좋아졌지만 링크·전화번호가 다시 답변에 포함됨
- Q357 O는 저축은행 상품 질문인데 보험회사 상품 설명이 많이 들어가 질문 초점이 흐려짐
- Q377 O는 간편송금 부분 근거를 놓쳐 해외계좌 설명에 치우침

따라서 “검색지표가 개선됐으므로 답변도 무조건 개선됐다”고 결론 내리면 안 됩니다. 별도의 답변 정답성·필수 항목 평가가 필요합니다.

## 9. 가장 중요한 실험 설계 문제

89문항의 `gold_query_action`은 전부 다음과 같습니다.

```
SPLIT_KEEP_ORIGINAL
```

즉 평가데이터셋 자체가 권장하는 방식은:

```
복합질의를 분리하되 원문도 보존
```

입니다.

하지만 이번 실험은:

- O: 재작성 질의만 사용
- X: 원문만 사용

이므로 양극단 비교입니다.

따라서 다음 버전은 제3안이어야 합니다.

```
원문 질문
+ 재작성된 하위 검색 질의 2~4개
→ 함께 검색
→ 결과 융합
```

## 최종 판단

현재 결과만 놓고 보면:

- 질의 재작성은 복합질문 검색에 유효함
- 특히 서로 다른 업무가 섞인 질문에서 효과가 큼
- 하지만 원문을 버리면 일부 질문에서 큰 손실 발생
- 평균 1.23초의 재작성 시간이 추가됨
- 전체 서비스 레이턴시의 진짜 병목은 Answer Skeleton과 답변 생성
- 라우터의 과도한 CLARIFY가 검색 성능을 더 크게 제한하고 있음

따라서 최종 권장안은:

> 공통 라우팅 → 원문 보존 → 복합질의만 분리 재작성 → 원문+분리질의 결과를 순위 기반으로 융합
> 

입니다.

현재처럼 질의별 Min-Max 점수의 최댓값으로 합치면 서로 다른 검색 질의의 점수 비교가 불안정할 수 있습니다. 다음 실험에서는 원문과 분리질의를 함께 검색하고 `RRF` 또는 하위 질의별 최소 근거 보존 규칙을 적용하는 것이 적절합니다.

6개 버전 모두 제시했던 하드 게이트를 통과했습니다.

- 실행 성공률: 100%
- 검색 질의 생성 유효율: 100%
- 정상 질문의 잘못된 OOS: 0건
- 정상 질문의 잘못된 DIRECT: 0건
- Hard Filter: 0건
- 검색 불가능 질문 추가질문 Precision: 100%

### 1순위: V1.5

답변 생성기가 Top-5 문서를 사용하므로 Recall@5와 NeedCoverage@5가 중요합니다.

V1.5의 장점:

- Recall@5 최고
- NeedCoverage@5 최고
- 두 지표 모두 V1.0 대비 통계적으로 유의한 개선
- V1.4와 지연시간 동일
- 동일 업무 복합질문을 건드리지 않음
- V1.6처럼 AllNeeds를 떨어뜨리지 않음

따라서 실제 검색→답변 파이프라인 후보는 다음 형태가 적절합니다.

```
단일질의 또는 동일 업무 복합질의
→ 원문 검색

서로 다른 업무가 포함된 고신뢰 복합질의
→ LLM 구조화 분해
→ 원문 0.4 + 하위질문 합 0.6 Weighted RRF

분해 검증 실패
→ 원문 검색으로 fail-open
```
